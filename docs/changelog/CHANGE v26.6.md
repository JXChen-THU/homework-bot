## 🎯 v26.6 要解决的问题

用户反馈的原话是：「exe 等待时间太长了，要不要加一个检测是否有数据文件，如果没有就马上弹出窗口并且不进行数据刷新，在账号密码填写好后进行正常行为。」

这句话指向的是一个真实且可复现的体验问题。首次运行（或在一台干净的机器上首次运行）时：

- `data/` 里没有任何 `*_session.json`；
- `sites.yaml` 里的账号密码还是空的（模板就是空串）。

程序却照样走完整流程：

1. `wait_for_network(timeout=120)` —— 没网/网络慢时**白等最多 120 秒**，这是启动路径上唯一会播报文字、也是唯一会在最前面阻塞的一步；
2. 为**每个**启用站点拉起一个 Playwright 浏览器去「抓作业」，而每个站点都要等登录页超时才放弃（数秒到数十秒）；
3. 结果必然是「需要登录」——用户等了半分钟到两分钟，等到的是一条本来一开始就能告诉他的提示。

而且默认启动行为是「静默」，所以**等的时候连窗口都没有**：用户看到的是"双击以后很久什么都没发生"。

## 🚀 v26.6 主要改进

### 1. 首启闸门：没有数据文件就不抓，直接显示窗口

判定口径（与用户逐条确认过）：

> **没有任何可用会话文件，且没有任何站点填了能解密出来的账号密码** → 这一轮不发任何网络请求、不启动浏览器，立即显示主窗口，并给出「去填账号密码」的引导。

只要还有**任意一个**启用站点存在会话文件、或填了可用账密（下次能静默登录），就完全按原来的流程正常抓取。

实现位置：

- `core/site_runner.py`：`startup_gate()` 是唯一判定入口，配 `data_file_present()` / `_site_has_usable_session()` / `_site_has_credentials()` / `_site_credentials_broken()` 几个小函数；
- `core/controller.py`：`Api.get_homeworks()` 在**调用 `fetch_all()` 之前**先问一次闸门；命中就直接返回 `{"gate": {...}}`。

命中闸门时做了什么、**没做**什么（有断言脚本逐条覆盖）：

| | 行为 |
|---|---|
| 网络等待 | **不执行**（`wait_for_network` 调用次数 = 0） |
| 站点抓取 / 浏览器 | **不执行**（`fetch_all` 调用次数 = 0） |
| 后台重登 | **不执行**（`auto_relogin_site` 调用次数 = 0） |
| 窗口 | 立即 `show_main_window()`，**静默档也显示** |
| 任务数据 | **不清缓存**；缓存里的站点任务 + `homework.db` 的手动任务照常返回 |
| 首轮网络等待 | 复位成「还没等过」，留给用户填完账号密码后的第一次真正抓取 |

### 2. 「静默」改回默认关：它该是用户的选择，不是默认值

- 旧默认：`STARTUP_MODE_DEFAULT = "silent"`，模板也写死 `startup_mode: silent`。
  后果是**第一次运行的人什么都没看见**——而这时他恰恰最需要看见窗口。
- 新默认：`visible`。`sites.yaml.template` 同步改成 `startup_mode: visible` 并更新了注释。
- **兼容**：配置里没有 `startup_mode` 这个键时，按「有没有数据文件」区分——
  - 已经有会话文件（老用户，程序在他机器上正常用过）→ 沿用 `silent`，**升级不改变既有行为**；
  - 一个会话文件都没有（全新机器，他从未做过这个选择）→ `visible`。
- 一旦用户在设置里动过这个开关，`sites.yaml` 里就有了这个键，之后一律以用户的值为准。

### 3. 引导条与空态：不让"没有数据"看起来像"没有作业"

命中闸门时主窗口顶部显示一条引导（`.banner.setup`）：

- 一句说清现在是什么状态（"这是第一次运行：还没有任何登录状态…"）；
- 三步下一步：① 点站点按钮填账号密码（雨课堂只能扫码，先不用管）② 填完自动开始抓取 ③ 只想手动记作业就直接「添加任务」；
- 每个待配置站点一行按钮，按钮文案/话术复用既有的 `LOGIN_HINTS`（不新增第二套话术表）；
- 一个「打开设置」按钮。

同时任务列表的空态也不再借用绿色那句「所有任务都已完成，太棒了！」——
首次运行时列表为空**不是**"没事可做"，而是"还没登录"。这句话以前会把用户误导成"程序已经没事干了"。

### 4. 顺手修掉的两处既有问题

- **手动任务曾经会丢**：短路分支如果直接返回 `_items_cache`，用户上次会话里加过的手动任务（只存在 `homework.db`，不在缓存里）就会凭空消失。现在短路与正常路径共用 `_merge_cached()`，都从 DB 读手动任务。
  这条在实现过程中被独立核验抓到过一个更隐蔽的变体，值得记下来：
  **短路分支只读缓存、却不写回缓存**，而 `add_task` / `toggle_done` / `delete_task` 结尾的 `_sync_main()` 是拿 `_items_cache` **整体覆盖**前端列表的。
  于是纯手动任务用户（引导条推荐的用法之一）勾一下复选框，列表当场被刷空（DB 里其实还在），再点刷新还会出现一条重复行 —— 缓存与返回值不一致，比"数据丢了"更像"程序坏了"。
  现在短路分支返回前会把合并结果写回 `_items_cache`，`_merge_cached()` 也做成**幂等**（按 uid 去重、保留 `manual` 标记），正常路径同样受益。
- **抓取结果没有去重**：适配器把同一个作业从两个入口返回时，列表里会出现两行。正常路径现在按 `uid` 去重（uid 为空的条目不参与，避免把本来不同的作业合成一条）。

### 5. 闸门自己出错时不许吞掉抓取
`startup_gate()` 的定位是"少做一次注定失败的抓取"，所以它**任何一步出问题都必须放行**：
- 配置读不出来（`config_error()`）→ 不短路，交给 `fetch_all()` 报"配置坏了"，用户不会看到"没有任务"的假象；
- 站点级判断抛异常（例如 `adapters.auth` 导入失败、DPAPI 解密整体异常）→ 不短路。
  `_site_has_credentials()` 因此返回**三态** `True/False/None`：`None` 表示"判断不出来"。
  早期实现里异常被吞成 `False`，所有站点都会看起来"没填账密"，闸门就会把一轮本该执行的抓取吞掉 —— 这是 fail-closed，方向反了。

### 6. 会话预检提速：15 秒 → 1 秒（第二项需求）

用户反馈："等待过去会话是否可复用是否要填账密的时间太长了，要 15s，改成 5s 吧"。

先量了一下，发现**那 15 秒全是干等**：无头请求实测 `learn` 首页 0.10 秒返回，而且最终 URL
**已经变成 `/f/login`**（会话失效时浏览器是被服务端直接跳到登录页的）。
代码却在校验"作业列表出现没有"—— 这个条件在登录页上永远不会成立，所以只能把 15 秒睡满。

改动（`adapters/auth.py` + 5 个适配器）：

- 新增 `page_on_login_page()`，并在 `wait_for_ready()` 的每轮轮询里检查：
  **一确认页面在登录页/认证页上就立即结束等待**，不再睡满；
- `SESSION_PROBE_MS = 1000`（会话预检上限）、`DATA_READY_MS = 15000`（数据就绪）；
- 5 个适配器（learn / thuoj / unipus / tyche / smartestu）的 `15000`（smartestu 是 `20000`）
  拆成"预检 1 秒 + 必要时数据 15 秒"两段，并去掉超时后那段固定补等待
  （learn 3 秒 / thuoj 2 秒 / smartestu 2 秒 —— 慢页面已由数据时限覆盖，补等待只拖慢"会话失效"这条路径）。

**为什么数据那段反而从 15 秒改回来、不再往下压**：超时值以前同时承担了两件事——
"会话还有没有用"和"数据来没来"。现在前者由早退负责，后者才是超时该管的，
所以超时**不需要**卡得很紧；反倒是卡得越紧，越容易把"慢"误判成"失效"。

> **同一版本内的后续更正**：这个"不再往下压"的结论被用户推翻了 ——
> 用户要求把数据等待从 15 秒改成 **5 秒**（`DATA_READY_MS = 5000`），并且超时后
> 不再只报错、而是自动清登录记录并静默重登一次（见下文第 9 条）。也正因为超时
> 现在会触发真实重登，"卡得越紧越容易误伤"这个权衡变得更敏感：慢站点会更频繁地
> 走一次真实的重新登录。

### 7. 超时不再等于"去重新登录"（这条才是根因）

> **⚠️ 同一版本内的后续更正（本节结论已被反转）**：用户随后明确要求
> "把慢的网站也别直接报错了，超时之后就自动清除登录记录重新登陆"。现在超时
> （`FetchFailedError.timeout=True`）会**清掉该站点登录记录并静默重登一次**，
> 见下文第 9 条。本节保留的是"当初为什么没那么做"的推理过程，下面的表格、文案
> 与底账都以第 9 条为准；历史叙述不改写。

改动 6 之后还剩一个更根本的问题。原来的判定是：

```text
预检超时 → 判 _is_logged_in() == False → raise LoginRequiredError
                                          → 触发后台静默重登（每站 10~60 秒，还可能弹窗）
```

而 `_is_logged_in()` / `_on_logged_in_page()` 返回 False 有**两种**原因：
"会话真失效"和"页面根本没来得及加载"。超时属于后者，却被当成了前者 ——
所以**任何**超时值都会误伤慢站点，把 15 改成 8 只是换个概率。

现在按"信号强度"分流（`adapters/*.py`）：

| 现象 | 判定 | 后果 |
|---|---|---|
| 页面明确跳到登录页 / SSO 页 | `LoginRequiredError` | 该重登就重登（且通常 1 秒内就判出来） |
| 接口明确 401 / 403 | `LoginRequiredError` | 同上（unipus / tyche / smartestu 的接口都是硬信号） |
| 等了 `DATA_READY_MS` 仍没内容、又**没有任何**失效信号 | `FetchFailedError(timeout=True)` | 当时：报"抓取超时"、**不触发重登**（**已被第 9、10 条反转**：现在任何报错都重登，最多连续 3 次；超时先清登录记录） |

文案由 `auth.timeout_detail()` 统一给（5 个站点共用一句，不各写一遍）：

> 「网络学堂页面 在 15 秒内没有返回内容。可能是网络或平台较慢，也可能登录状态已失效 ——
> 如果点「刷新任务」重试仍不行，请点「登录」重新登录一次。」

两头都说，是因为这种超时**真的判不出来**：说"你要重新登录"会把慢站点引去做一次白重登；
说"没问题"则万一是真失效，用户就没有出口。

> ⚠️ 这里必须留个底账：`FetchFailedError` 在 `site_runner._fetch_one_site_locked` 里
> 走的是"只播报错误"分支（`except Exception`），**不会**触发 `auto_relogin_site`。
> 这是刻意的，也正是这条改动的意义所在。

**为什么敢把预检压到 1 秒**：只有当"页面确实在登录页上"时才提前结束，
所以"页面只是慢"不会被误判成会话失效；而一旦误判就会触发一次白跑的重登（更慢、还可能弹窗）。
这也是必须给数据阶段留足 15 秒的原因。

**实测（真实无头 Edge，同一个空会话文件）**：

| | 改动前 | 改动后 |
|---|---|---|
| 等待部分 | 19.1s（15s 超时 + 3s 补等待 + 约 1s 导航） | **0.69s**（预检命中登录页，当场返回） |
| 端到端（`learn.fetch_homeworks`） | 约 26s | 7.27s |

**为什么端到端还剩 7 秒 —— 一个必须说清的发现**：其中约 **6.5 秒是 `browser_session`
退出时关浏览器的固定成本**，与本次改动无关：

```text
只启动不干活            退出 0.65s
about:blank + context  退出 0.63s
真实访问过网络学堂       退出 6.96s   ← 只有真的访问过网站才慢
直接调 browser.close()  1.47s        ← 慢的不是 close 本身，是 playwright 整体退出
```

也就是说，"每次抓取固定约 7 秒、与站点和网络无关"的这笔开销仍然存在，
它不在这条 15 秒超时里，属于另一个问题（若要继续提速，应从"浏览器生命周期"下手，
例如一次抓取共用浏览器或把退出移出关键路径）。

### 8. 红窗取消"过期 3 天"下限：过期多久都算紧急（用户要求）

v26.5给红窗加过一个下限 `URGENT_PAST_GRACE_HOURS = 72`（过期超过 3 天的降级到白窗）。
**用户明确要求取消它**，所以：

- `core/task_logic.py` 删掉该常量，`compute_urgent` 只判上界：未完成、`end` 能解析、
  `hours_left <= 24` 就进红窗，**包括已经过期任意久的任务**；文件头注释保留了这段历史。
- 已知副作用（用户已知悉并接受）：列表按 `hours_left` 升序，过期越久越靠前，
  所以最陈旧的作业会出现在红窗最上面几行；红窗一次最多显示 8 条。
- 文档同步：README 的功能列表与「红色浮窗没有显示？」一问都改成了"所有已过期都算紧急"。

### 9. 超时后自动清除登录记录并静默重登（用户要求，反转第 7 条）+ 数据等待 15 秒 → 5 秒

用户需求原文两句：

> 「把慢的网站也别直接报错了，超时之后就自动清除登录记录重新登陆」
> 「而且把 15s 改成 5s」

**判定层**（`adapters/base.py`）：`FetchFailedError` 新增 `timeout` 标记，
只有"等满 `DATA_READY_MS` 仍没内容、又**没有任何**失效信号"这一类才置 `timeout=True`
（6 个抛出点：learn / thuoj / tyche / unipus / smartestu ×2）。接口 5xx、页面结构变化
仍然是 `timeout=False`。

**处置层**（`core/site_runner.py`）：`_should_relogin_after_timeout()` 决定要不要
"清登录记录 + 重登"，四个条件缺一不可：

| 条件 | 为什么必须 |
|---|---|
| `exc.timeout is True` | 5xx / 结构变化不代表会话失效，不拿用户的登录状态去赌 |
| 平台支持账密自动登录 | 雨课堂只能扫码，清掉会话等于把用户踢下线 |
| 有可用账密 | 没有账密就登不回来，报一条错误比"变成需要登录"更好 |
| 账密能在本机解密 | 换了电脑 / 换了 Windows 账户时密文解不开，同样登不回来 |

命中则 `_discard_session(reason=…)` 清掉会话文件，然后走**已有的**静默重登分支：
重登成功 → 立刻重新抓一次；失败 → 照旧给出 `need_login` 与原因话术。
`_discard_session()` 的日志文案改成由调用方传 `reason`，免得在超时路径上
说"会话文件损坏"这种假话。

**时间**（`adapters/auth.py`）：`DATA_READY_MS = 5000`（原 15000），
`wait_for_ready()` 的默认值同步改成 5 秒；`timeout_detail()` 的文案现在说的是
"在 5 秒内没有返回内容"，也不再声称"程序不会自动重登"。

**代价（必须说清楚）**：数据窗口 15 秒 → 5 秒、且超时即重登，意味着**慢站点更容易
触发一次真实的重新登录**（每站 10~60 秒，清华 SSO 还可能弹窗）。这是用户明确选择的
取舍：宁可让它自己重登一次，也不要停在"抓取超时"上。

**本条的验证**（离线探针，18 条断言全过；断言脚本按项目惯例不入库）：
超时+有账密 → 会话被清、重登 1 次、重试成功（2 次 fetch、1 条、0 报错）；
接口 500 → 不重登、会话保留、照常报错；超时但没账密 → 不重登、会话保留；
超时但平台不支持账密登录 → 不重登、会话保留；超时但账密解不开 → 不重登、会话保留；
`DATA_READY_MS == 5000` 且超时文案为 5 秒。**未**用真实站点做端到端（需要真实账密）。

> 第 10 条把这里的"只对超时重登"放宽成了"任何报错都重登"，清登录记录仍只对超时。

### 10. 任何报错都尝试重登，最多连续 3 次（用户要求，进一步反转第 7 条）

用户要求原文：

> 「不要，只要报错什么就尝试重登，最多连续重登三次」

**规则**（`core/site_runner._fetch_one_site_locked` 改写成"抓取 → 失败则重登 → 再抓"
的有界循环）：

| 失败类型 | 重登前是否清登录记录 | 之后 |
|---|---|---|
| 页面跳登录页 / 接口 401、403（`LoginRequiredError`） | 不清 | 重登；失败则提示"需要登录" |
| 会话文件损坏 | 清（自愈，原有行为） | 重登；失败则提示"需要登录" |
| 超时（`FetchFailedError.timeout=True`） | **清** | 重登；失败则报"抓取超时" |
| 接口 5xx / 页面改版 / Playwright 崩溃 | 不清 | **也重登**；失败则照实报错 |

循环上限 `RELOGIN_MAX_CONSECUTIVE = 3`：一次刷新里最多连续重登 3 次（最多 4 次抓取）。
上限是必需的 —— `auto_relogin_site()` 在**登录成功**时会清掉冷却，如果平台一直 5xx，
"报错 → 重登 → 再报错"会无限转下去，一次刷新就卡死了。`auto_relogin_site()` 自己
仍然拦三种情况：平台不支持账密登录、没有可用账密、刚失败过的冷却期
（需要验证码 10 分钟 / 账密不对 30 分钟）。

**代价（必须说清楚）**：这是最激进的一档 —— 接口 500 也会触发真实重登
（每站 10~60 秒，清华 SSO 可能弹窗），最坏情况一个站点在一次刷新里要花掉三次登录的
时间。这是用户明确选择的取舍：宁可反复重登，也不要停在报错上；冷却机制是唯一的刹车。

**本条验证**（离线探针，13 条断言全过；脚本按项目惯例不入库）：

| 场景 | 期望 | 实测 |
|---|---|---|
| 500 + 有账密，重登一次后抓取成功 | 重登 1 次、抓 2 次、无报错、**不清**会话 | ✓ |
| 一直 500，重登一直成功 | 正好重登 3 次、抓 4 次，最后照实报错 | ✓ |
| 超时 | 重登前**已清**会话；重登后抓取成功 | ✓ |
| 需要登录 + 重登成功 | 抓到数据，既不报错也不提示 | ✓ |
| 需要登录 + 登不回来 | `need_login=1`、`errors=0` | ✓ |
| 没有账密 | 只抓 1 次、直接报错，不进重登循环 | ✓ |
| 重登返回 False（冷却中） | 立刻收手，不再抓 | ✓ |

### 11. 密码错误立刻提示、不重复登录（用户要求）

用户要求原文：

> 「我专门改错密码，你要在收到密码错误的时候就直接提示出来，不要重复登录」

平台对"密码错"是有**明确信号**的 —— `adapters/auth.py` 会读登录页上的错误元素与正文
（例如清华 SSO 的「您的用户名或密码不正确，请重试！」），直接返回 `reason="bad_credentials"`，
不需要靠"再试一次"来确认。两处改动：

1. **不再开第二次登录**（`_auto_relogin_locked`）：无头层已经拿到 `bad_credentials` 时，
   立刻记失败并返回，**不再**去走"屏幕外真实窗口"那一层 —— 密码错了换个窗口也不会变对，
   原来白花 10~60 秒、还可能闪一下窗。
   例外说清楚：`learn` / `thuoj`（清华 SSO）的 `LOGIN.skip_headless = True`，本来就跳过
   无头层、只有屏幕外一层，所以它们本来就只登一次；受这条影响的是
   `smartestu` / `tyche` / `unipus`。
2. **直接把这句话交给用户**（`_fetch_one_site_locked`）：重登失败原因是"用户能修"的
   凭据类问题（`bad_credentials` / `school_select_failed` / `no_credentials` /
   `session_save_unusable`，即 `_CREDENTIAL_FAILURE_REASONS`）时，结果走 `need_login`
   而不是 `errors` —— 否则用户看到的是原始抓取错误（"抓取超时"、"作业接口 HTTP 500"），
   真正的原因"密码错了"被盖在下面。

用户看到的文案（前端 `LOGIN_HINTS.bad_credentials`）：

> 自动登录失败，账号或密码可能不对，请点按钮重新填写　｜　按钮：**重新填账号密码**

之后该站点进入 **30 分钟冷却**（`_RELOGIN_COOLDOWN_S["bad_credentials"] = 1800`），
期间刷新不会再发起登录；把密码改对并在设置里保存后会清掉冷却与失败原因，立即恢复。

**本条验证**（离线探针，13 条断言全过；脚本按项目惯例不入库）：

| 场景 | 期望 | 实测 |
|---|---|---|
| 先无头站点（tyche）无头层返回 bad_credentials | 只调用 1 次登录、**不开**屏幕外窗口、冷却 30 分钟 | ✓ |
| 同上但无头层只是 timeout | 仍然会试屏幕外窗口（这不是密码问题） | ✓ |
| 清华 SSO 站点（learn，跳过无头）返回 bad_credentials | 本来就只登 1 次、冷却生效 | ✓ |
| 抓取要登录 + 密码错 | 抓 1 次、登 1 次；直接给 `need_login(reason=bad_credentials)` | ✓ |
| 第二次刷新（冷却期内） | **一次登录都不发**，提示不变 | ✓ |
| 超时 + 重登发现密码错 | 显示"密码错"，"抓取超时"不顶在前面 | ✓ |
| 重登失败于非凭据原因（登录超时） | 照实报原始抓取错误，不误报"需要登录" | ✓ |

> **⚠️ 第 12 条修掉了这一条的一个漏洞**：它只在"重登会真正提交密码"时才成立。旧代码在
> `LoginRequiredError` 这条**最常见**路径上没有丢弃旧会话，`silent_login` 会复用它并回
> `session_valid`，于是白转三轮、几十秒都判不出密码错。详见第 12 条。

### 12. 修掉「重登白转三轮、密码错几十秒才报」的缺陷 + 登录流程提速（用户要求：整套十几秒内）

用户反馈原文：

> 「我希望账号密码错误在第一遍就爆出，不重跑……就是说给出账号密码错误的时间太长了，
>   我希望整套流程控制在十几秒，不然用户一直在等」

**根因（是真 bug，不是参数没调好）**：`silent_login()` 的第一步是"复用会话检查"
（`adapters/auth.py` step 1）—— 带着已有会话打开站点首页，能通过校验就直接返回
`(True, "session_valid")`。而重登恰恰是抓取**刚失败之后**发起的，那份会话正是刚刚判失败的
那一份：

```text
抓取失败 → 重登（复用旧会话 → session_valid → 被当成"重登成功"，密码从未被提交）
        → 重试抓取又失败 → 再重登 …… 一直转满 RELOGIN_MAX_CONSECUTIVE = 3 次
```

全程几十秒，而且**密码根本没被提交过**，所以永远判不出"密码错"。

**修法**：把"丢弃旧会话"从"只对超时"改成**决定重登就丢**，并放进重登循环里统一处理
（覆盖 `LoginRequiredError` 这条最常见路径）。丢之前先确认"真的会发起登录"：

| 前置条件 | 是否丢会话 / 重登 |
|---|---|
| 该站点在失败冷却期内 | 不丢、不登（免得白白把用户踢下线） |
| 没填账密 / 平台不支持账密登录 / 账密在这台机器解不开 | 不丢、不登 |
| 以上都不成立 | **丢**掉刚判失败的会话 → 发起一次**真实**登录 |

**登录提速**：把登录流程里的固定 `wait_for_timeout` 换成"元素出现就走"（新增
`auth._wait_for_any()` / `_wait_form()`，等待上限不变）：

| 站点 | 原来的固定等待 | 现在 |
|---|---|---|
| 网络学堂 | goto 后 2500ms + 点入口后 4000ms | 等入口/表单出现即继续（实测约 1.3s 就填上表单） |
| 清华 OJ | 2500 + 1200 + 5000ms | 同上 |
| U 校园 | 4000 + 6000ms | 同上 |
| 数你最灵 / Tyche | 3500 / 2500ms | 同上 |

**实测（本机、网络学堂、故意填错密码、流程完全真实）**：

| 阶段 | 耗时 |
|---|---|
| 抓取（会话预检 1s + 数据等待 5s + 浏览器启停） | 约 6.5s |
| 真实重登 —— 其中**判定"密码错"只用 2.1s**，其余 6.5s 是 Playwright 退出浏览器的固定开销 | 约 8.6s |
| **首轮合计** | **15.1s** |
| 第二次刷新（冷却期内） | **0.0s**（直接给提示，不再登录） |

**剩下的那约 6.5 秒**：只有真正访问过网站的浏览器退出才这么慢（`browser.close()` 本身
1.47s，慢的是 Playwright 整体退出）。要再压下去必须改浏览器生命周期（一次抓取共用驱动、
或把退出移出关键路径），属于另一件事。

**本条验证**（离线探针，17 条断言全过；断言脚本按项目惯例不入库）：

| 场景 | 期望 | 实测 |
|---|---|---|
| **关键回归**：`LoginRequiredError` + 旧会话"看起来仍可用" | 只登录 1 次、真的提交了密码、第一轮给出 `bad_credentials`、旧会话被丢弃 | ✓ |
| 没填账密 | 不丢会话、不登录，提示 `no_credentials` | ✓ |
| 雨课堂（不支持账密登录） | 不丢会话、不登录，提示 `qr_code` | ✓ |
| 冷却期内 | 不丢会话、一次登录都不发，仍提示 `bad_credentials` | ✓ |
| 500 + 重登成功 | 丢会话 → 重登 1 次 → 重抓成功 | ✓ |
| 登录一直成功但抓取一直失败 | 仍然最多 3 次重登 / 4 次抓取，最后照实报错 | ✓ |

7. **密码填错会立刻提示、不会反复登录**：平台明确回"用户名或密码不正确"时当场停下，
   显示「自动登录失败，账号或密码可能不对」（按钮：重新填账号密码），30 分钟内不再自动登录。
