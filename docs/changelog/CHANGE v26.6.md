## 🎯 v26.6 要解决的问题

用户原话：

> 「exe 等待时间太长了，要不要加一个检测是否有数据文件，如果没有就马上弹出窗口并且不进行数据刷新，在账号密码填写好后进行正常行为。」

这句话指向一个真实且可复现的体验问题。首次运行（或在一台干净的机器上首次运行）时，`data/` 里没有任何 `*_session.json`，`sites.yaml` 里的账号密码还是模板里的空串，程序却照样走完整流程：

1. `wait_for_network(timeout=120)` —— 没网或网络慢时**白等最多 120 秒**，这是启动路径上唯一会在最前面阻塞的一步；
2. 为**每个**启用站点拉起一个 Playwright 浏览器去「抓作业」，每站都要等登录判定超时才放弃（数秒到数十秒）；
3. 结果必然是「需要登录」—— 用户等了半分钟到两分钟，等到的是一条一开始就能告诉他的提示。

而且默认启动行为是「静默」，**等的时候连窗口都没有**：用户看到的是「双击以后很久什么都没发生」。

后续几轮反馈把范围扩大成四件事：等待时间太长、失败之后反复重登（白转三轮）、界面会「显示获取完成却一直卡着」、以及 Tyche 的两类现场需要说清原因。本版按这四件事组织：**启动与首次运行 → 等待时间与失败处理 → 防卡死与错误反馈 → 界面与文案 → 仓库与包体**。

## 🚀 一、启动与首次运行

### 1.1 首启闸门：没有数据文件就不抓，直接显示窗口

判定口径（与用户逐条确认过）：

> **没有任何可用会话文件，且没有任何站点填了能解密出来的账号密码** → 这一轮不发任何网络请求、不启动浏览器，立即显示主窗口，并给出「去填账号密码」的引导。

只要还有**任意一个**启用站点存在会话文件、或填了可用账密（下次能静默登录），就完全按原来的流程抓取。

实现位置：`core/site_runner.py` 的 `startup_gate()` 是唯一判定入口，配 `data_file_present()` / `_site_has_usable_session()` / `_site_has_credentials()` / `_site_credentials_broken()`；`core/controller.py` 的 `Api.get_homeworks()` 在**调用 `fetch_all()` 之前**先问一次闸门，命中就直接返回 `{"gate": {...}}`。

命中闸门时做了什么、**没做**什么（有断言脚本逐条覆盖）：

| | 行为 |
|---|---|
| 网络等待 | **不执行**（`wait_for_network` 调用次数 = 0） |
| 站点抓取 / 浏览器 | **不执行**（`fetch_all` 调用次数 = 0） |
| 后台重登 | **不执行**（`auto_relogin_site` 调用次数 = 0） |
| 窗口 | 立即 `show_main_window()`，**静默档也显示** |
| 任务数据 | **不清缓存**；缓存里的站点任务与 `homework.db` 的手动任务照常返回 |
| 首轮网络等待 | 复位成「还没等过」，留给用户填完账号密码后的第一次真正抓取 |

### 1.2 闸门自身出错时必须 fail-open

`startup_gate()` 的定位是「少做一次注定失败的抓取」，所以它**任何一步出问题都必须放行**：配置读不出来（`config_error()`）→ 不短路，交给 `fetch_all()` 报「配置坏了」，用户不会看到「没有任务」的假象；站点级判断抛异常（例如 `adapters.auth` 导入失败、DPAPI 整体异常）→ 不短路。`_site_has_credentials()` 因此返回**三态** `True` / `False` / `None`，`None` 表示「判断不出来」。

> **踩过的坑**：早期实现把异常吞成 `False`，于是所有站点都看起来「没填账密」，闸门会把一轮本该执行的抓取吞掉 —— 这是 fail-closed，方向反了。

### 1.3 「静默」改回默认关：该由用户自己选

- 旧默认 `STARTUP_MODE_DEFAULT = "silent"`，模板也写死，后果是**第一次运行的人什么都没看见** —— 而这正是他最需要看见窗口的时候；新默认 `visible`，`sites.yaml.template` 同步改成 `startup_mode: visible` 并更新注释。
- **兼容**：配置里没有 `startup_mode` 这个键时，按「有没有数据文件」区分 —— 已有会话文件（老用户，程序在他机器上正常用过）→ 沿用 `silent`，**升级不改变既有行为**；一个会话文件都没有（全新机器，他从未做过这个选择）→ `visible`。
- 用户在设置里动过这个开关后，`sites.yaml` 里就有这个键，之后一律以用户的值为准。

### 1.4 引导条与空态：别让「没有数据」看起来像「没有作业」

命中闸门时主窗口顶部显示一条引导（`.banner.setup`）：一句说清当前状态（「首次启动：尚未检测到登录状态…」）；三步下一步 —— ① 在下方选择站点并填写账号密码（雨课堂仅支持扫码登录，可暂不配置）② 配置完成后将自动开始抓取，也可随时执行「刷新任务」③ 如需手动记录任务，可使用「添加任务」，无需登录任何站点；每个待配置站点一行按钮，按钮文案与话术复用既有的前端 `LOGIN_HINTS`（不新增第二套话术表）；一个「打开设置」按钮。

同时任务列表的空态不再借用绿色那句「所有任务都已完成，太棒了！」—— 首次运行时列表为空**不是**「没事可做」，而是「还没登录」，那句话会把用户误导成「程序已经没事干了」。

### 1.5 顺手修掉的两处既有问题

- **手动任务曾经会丢**：短路分支如果直接返回 `_items_cache`，用户上次会话里加过的手动任务（只存在 `homework.db`，不在缓存里）就会凭空消失。现在短路与正常路径共用 `_merge_cached()`，都从 DB 读手动任务。
- **抓取结果没有去重**：适配器把同一个作业从两个入口返回时，列表里会出现两行。正常路径现在按 `uid` 去重（uid 为空的条目不参与，避免把本来不同的作业合成一条）。

> **踩过的坑（更隐蔽的变体）**：短路分支只读缓存、却**不写回**缓存，而 `add_task` / `toggle_done` / `delete_task` 结尾的 `_sync_main()` 是拿 `_items_cache` **整体覆盖**前端列表的。于是纯手动任务用户勾一下复选框，列表当场被刷空（DB 里其实还在），再点刷新还会出现一条重复行 —— 缓存与返回值不一致，比「数据丢了」更像「程序坏了」。现在短路分支返回前会把合并结果写回 `_items_cache`，`_merge_cached()` 也做成**幂等**（按 uid 去重、保留 `manual` 标记）。

## ⚡ 二、等待时间与失败处理

这一节是本版改动最集中的地方，也是用户反复迭代的部分：**先把「干等」找出来，再决定失败之后做什么。**

### 2.1 超时不再等于「去重新登录」（这条才是根因）

原来的判定链是「预检超时 → 判 `_is_logged_in() == False` → `raise LoginRequiredError` → 触发后台静默重登（每站 10~60 秒，还可能弹窗）」。而 `_is_logged_in()` 返回 `False` 有**两种**原因：「会话真失效」和「页面根本没来得及加载」；超时属于后者，却被当成了前者 —— 所以**任何**超时值都会误伤慢站点，把 15 秒改成 8 秒只是换个概率。于是按**信号强度**分流：

| 现象 | 判定 | 后果 |
|---|---|---|
| 页面明确跳到登录页 / SSO 页 | `LoginRequiredError` | 该重登就重登（通常 1 秒内就判出来） |
| 接口明确 401 / 403 | `LoginRequiredError` | 同上（unipus / tyche / smartestu 的接口都是硬信号） |
| 等满 `DATA_READY_MS` 仍没内容、又**没有任何**失效信号 | `FetchFailedError(timeout=True)` | 标记为「超时」这一类（处置见 2.3、2.4） |

超时文案由 `adapters/auth.timeout_detail()` 统一给（5 个站点共用一句，不各写一遍），两头都说，因为这种超时**真的判不出来**：说「你要重新登录」会把慢站点引去做一次白重登，说「没问题」则万一是真失效，用户就没有出口。

### 2.2 会话预检 15 秒 → 1 秒

用户原话：**「等待过去会话是否可复用是否要填账密的时间太长了，要 15s，改成 5s 吧」**。

先量了一下，发现**那 15 秒全是干等**：无头请求实测 `learn` 首页 0.10 秒返回，而且最终 URL **已经变成 `/f/login`**（会话失效时浏览器是被服务端直接跳到登录页的）；代码却在校验「作业列表出现没有」—— 这个条件在登录页上永远不会成立，所以只能把 15 秒睡满。改动（`adapters/auth.py` + 5 个适配器）：

- 新增 `page_on_login_page()`，在 `wait_for_ready()` 每轮轮询里检查：**一确认页面在登录页/认证页上就立即结束等待**；
- `SESSION_PROBE_MS = 1000`（会话预检上限）；5 个适配器（learn / thuoj / unipus / tyche / smartestu）的 15 秒（smartestu 原为 20 秒）拆成「预检 1 秒 + 必要时数据等待」两段，并去掉超时后那段固定补等待（learn 3 秒 / thuoj 2 秒 / smartestu 2 秒 —— 慢页面已由数据时限覆盖，补等待只拖慢「会话失效」这条路径）。

**实测（真实无头 Edge，同一个空会话文件）**：

| | 改动前 | 改动后 |
|---|---|---|
| 等待部分 | 19.1s（15s 超时 + 3s 补等待 + 约 1s 导航） | **0.69s**（预检命中登录页，当场返回） |
| 端到端（`learn.fetch_homeworks`） | 约 26s | 7.27s |

**为什么敢把预检压到 1 秒**：只有当「页面确实在登录页上」时才提前结束，所以「页面只是慢」不会被误判成会话失效；而一旦误判就会触发一次白跑的重登（更慢、还可能弹窗）。

> **踩过的坑**：第一版 URL 判定把**主机名**也当成登录页特征，结果 `learn` 全站皆中、每次抓取都被提前打断。现在的判定要求「路径或认证流程特征」且「不在站点自己的主机上」，并有 24 条断言 + 真实页面实测兜底（清华 OJ 课程主页判为非登录页、走满 1 秒预检；`learn` 未登录跳 `/f/login` 判为登录页并当场返回）。

### 2.3 数据等待 15 秒 → 5 秒，且超时改为「清会话 + 重登」

用户原话两句：**「把慢的网站也别直接报错了，超时之后就自动清除登录记录重新登陆」**「**而且把 15s 改成 5s**」。

- **判定层**：`adapters/base.FetchFailedError` 新增 `timeout` 标记，只有「等满 `DATA_READY_MS` 仍没内容、又**没有任何**失效信号」才置 `timeout=True`（6 个抛出点：learn / thuoj / tyche / unipus / smartestu ×2）；接口 5xx、页面结构变化仍是 `timeout=False`。
- **时间**：`DATA_READY_MS = 5000`（原 15000），`wait_for_ready()` 默认值同步；`timeout_detail()` 文案改为「在 5 秒内未返回内容…」。
- **处置**：命中超时后先丢弃该站点登录记录，再走静默重登（见 2.4）。

**代价（用户明确选择的取舍）**：数据窗口压到 5 秒、且超时即重登，意味着**慢站点更容易触发一次真实的重新登录**（每站 10~60 秒，清华 SSO 还可能弹窗）。宁可让它自己重登一次，也不要停在「抓取超时」上。

### 2.4 重登规则：只重登一遍，且重登前必须丢掉「刚判失败」的会话

用户原话（两轮）：

> 「不要，只要报错什么就尝试重登，最多连续重登三次」
> 「1.账号密码错误，立即爆出 2.系统报错的时候尝试重新登录一遍 3.没有填账号密码，如同填错，立即爆出 4.把之前的转三遍取消 5.既然 2.1s 就有答案，为什么不先报出来…」

**最终规则**（`core/site_runner._fetch_one_site_locked`：抓取 → 失败则重登 → 再抓的有界循环）：

| 失败类型 | 重登前是否丢登录记录 | 之后 |
|---|---|---|
| 页面跳登录页 / 接口 401、403（`LoginRequiredError`） | **丢** | 重登一遍；失败则提示「需要登录」 |
| 会话文件损坏 | 丢（自愈，原有行为） | 重登一遍；失败则提示「需要登录」 |
| 超时（`FetchFailedError.timeout=True`） | **丢** | 重登一遍；失败则照实报错 |
| 接口 5xx / 页面改版 / Playwright 崩溃 | 也丢 | **也重登**一遍；失败则照实报错 |

- **上限从 3 改成 1**（`RELOGIN_MAX_CONSECUTIVE = 1`）：一次刷新里最多重登 **1 遍**（最多抓 2 次）。上限本身是必需的 —— 登录成功会清掉冷却，若平台一直 5xx，「报错 → 重登 → 再报错」会无限转下去。
- **无头层返回 `timeout` 时不再试屏幕外第二层**：屏幕外窗口的用途是绕过「反无头」（表现是验证码/二次验证页，`reason` 为 `mfa` / `no_login_form`），而不是「慢」。这条把最坏情况从两轮预算压到一轮。
- 丢之前先确认「真的会发起登录」：

| 前置条件 | 是否丢登录记录 / 重登 |
|---|---|
| 该站点在失败冷却期内 | 不丢、不登（免得白白把用户踢下线） |
| 没填账密 / 平台不支持账密登录 / 账密在这台机器解不开 | 不丢、不登 |
| 以上都不成立 | **丢**掉刚判失败的会话 → 发起一次**真实**登录 |

> **踩过的坑（本版最重要的一个真 bug）**：`silent_login()` 的第一步是「复用会话检查」—— 带着已有会话打开站点首页，能通过校验就直接返回 `(True, "session_valid")`。而重登恰恰是抓取**刚失败之后**发起的，那份会话正是刚刚判失败的那一份：抓取失败 → 重登（复用旧会话 → `session_valid` → 被当成「重登成功」，密码从未被提交）→ 重试抓取又失败 → 再重登 …… 一直转满 3 次。全程几十秒，而且**密码根本没被提交过**，所以永远判不出「密码错」—— 用户看到的是「重登三遍才跳账号密码错误」。根因是「丢弃旧会话」当时只加在通用异常分支里，而**最常见**的 `LoginRequiredError` 路径没有丢；修法是把丢弃动作放进重登循环统一处理。

### 2.5 凭据类失败第一遍就报，不重复登录

用户原话：**「我专门改错密码，你要在收到密码错误的时候就直接提示出来，不要重复登录」**。

平台对「密码错」有**明确信号**（登录页上的错误元素与正文，例如清华 SSO 的「您的用户名或密码不正确，请重试！」），所以不需要靠「再试一次」确认：

1. **不再开第二次登录**：无头层已经拿到 `bad_credentials` 时立刻记失败并返回，**不再**走屏幕外窗口那一层 —— 密码错了换个窗口也不会变对，原来白花 10~60 秒、还可能闪一下窗。例外：`learn` / `thuoj`（清华 SSO）的 `LOGIN.skip_headless = True`，本来就跳过无头层、只有屏幕外一层，所以它们本来就只登一次；受这条影响的是 `smartestu` / `tyche` / `unipus`。
2. **直接把这句话交给用户**：重登失败原因是「用户能修」的凭据类问题（`_CREDENTIAL_FAILURE_REASONS`：`bad_credentials` / `school_select_failed` / `no_credentials` / `session_save_unusable` / `basic_auth_failed`）时，结果走 `need_login` 而不是 `errors` —— 否则用户看到的是原始抓取错误（「抓取超时」、「作业接口 HTTP 500」），真正的原因被盖在下面。

用户看到的文案：**「自动登录失败：账号或密码有误，请重新填写」**（按钮：重新填写账号密码）。**冷却**（只放内存，重启即清）：需要验证码 **600 秒**、账号密码错 / Basic Auth 错 / 其余失败 **1800 秒**；期间刷新不再发起登录；在设置里重新保存账号密码会立刻清掉冷却与失败原因。

### 2.6 登录判定预算 60 秒 → 5 秒

用户原话：**「60s→5s」**。

- `silent_login(timeout_ms=5000)`：这是**「提交之后」**的预算，不含启动浏览器、打开登录页、填表的时间。
- 新增 `STUCK_FORM_MS = 3000`：提交 3 秒后仍停在**同一个**登录表单（URL 与提交时相同、输入框仍在）、且没有二次验证界面 ⇒ 判 `bad_credentials`。这条是给「报错文字不在已知标记里」的站点兜底的：Tyche 就是这种情况，旧逻辑每轮要轮询满 60 秒，最后只给出「登录超时」。

### 2.7 登录流程的固定等待改成「元素出现即继续」

新增 `auth._wait_for_any()` / `_wait_form()`（等待上限不变，只是不再白睡）：

## 🧯 三、防卡死、错误反馈与防呆

### 3.1 页面内请求加 8 秒上限：修「显示获取完成却一直卡着」

用户报障原话：**「然后为什么现在显示获取完成，但是有一个需要等了的时候一直卡住了」**。

**根因**：**Playwright 的 `page.evaluate` 不套用 default timeout**。适配器都在页面里用 `fetch()` 取接口（`learn` / `smartestu` / `thuoj` / `tyche` / `unipus` / `yuketang`），谁都没设超时 —— 服务器收下连接却一直不回包时，`evaluate` **永不返回**，抓取线程卡死：其它站点早就显示「已获取 N 条」，这个站点一直不动，刷新按钮也点不动（那一轮还占着抓取锁）。

修法：① 新增 `auth.guard_in_page_fetch(page)`，用 `add_init_script`（**每次导航之后都生效**）给页面里的 `window.fetch` 套 `AbortController`，超时 **8 秒**；6 个适配器与登录判定页面全部装上。② **进度区新增「仍在抓取 N 个站点：X、Y」** —— 进度区只保留最后 3 行，慢站点那一行会被后来完成的站点顶掉，界面上就成了「都显示已获取、却一直不动」，看着像卡死；现在只要有站点没完成就播报一句。

**验证（对着「收下连接但不回包」的服务器实测）**：

| 场景 | 结果 |
|---|---|
| 未装守护的页面内 fetch | 永久卡住（正是用户看到的症状） |
| 装了守护 | **8.0 秒** 抛 `AbortError`，转成一次可上报的失败 |
| `fetch_all` 两个站点、其中一个慢 | 播报「仍在抓取 1 个站点：Tyche」 |

### 3.2 Tyche 等太久：判定预算与凭据两条一起修

用户报障原话：**「为什么 Tyche 还是等了好久」**。根因：静默登录的判定预算是 60 秒，而 Tyche 的报错文字不在通用错误标记里（6 个适配器都没有自定义 `error_markers`），于是每轮都要轮询满 60 秒；判成 `timeout` 后还会再换屏幕外窗口重试一轮 —— 两轮就是两分钟。改动与效果：

| 改动 | 效果 |
|---|---|
| 判定预算 60 秒 → 5 秒（见 2.6） | 最坏一轮 5 秒 |
| `STUCK_FORM_MS = 3000`（见 2.6） | Tyche 这类站点也能在约 3 秒给出**正确**话术 |
| 无头层 `timeout` 不再试屏幕外窗口（见 2.4） | 一次刷新只等一轮 |
| `FetchFailedError(credentials=True)`：凭据被服务器拒（Basic Auth 回 401）→ 跳过重登、当场提示、进冷却、**保留**网站会话 | 不白跑一轮，提示也不再误导 |
| Tyche 主文档直接回 401 → 立刻按凭据错上报 | 判定从「6 秒探测 + 一次重登」变成 0.7 秒 |

**实测（真实网络；Tyche 整个站点在 Basic Auth 之后）**：没填 Basic 凭据 → 0.7 秒判定、明确提示「Basic Auth 未通过服务器校验」（总耗时 7.0 秒，其中约 6.3 秒是 Playwright 退出浏览器）；Basic 凭据填错 → **同样 7.0 秒、同样正确提示**（改前：白等 6 秒探测 → 误报「需要登录」→ 再白跑一次重登）。

### 3.3 Tyche 两类现场自动判类

用户把两种现场直接贴了过来：

| 现场（界面 + 诊断摘要） | 用户要求的处置 |
|---|---|
| 界面「登录页面无法打开，请检查网络后重试」，摘要里出现 `找不到登录输入框(user=None pass=None)` | 这说明 Tyche 的 **Basic Auth** 有问题 → 让用户重填 Basic Auth 账号密码 |
| 摘要里出现 `net::ERR_CONNECTION_TIMED_OUT at http://<Tyche 服务器>:6080/tyche` | 这说明**校园网/VPN 没连** → 告诉用户「无法连接上 Tyche，请使用校园 VPN 后重新刷新任务」 |

| 规则 | 实现 | 用户看到什么 |
|---|---|---|
| 登录页打开了、却没有账号密码输入框 | `tyche.LOGIN["no_form_means_basic_auth"] = True` ⇒ `silent_login` 返回新 reason **`basic_auth_failed`** | 「Tyche 的 Basic Auth 账号或密码有误，请重新填写」+ 按钮直接打开**重填凭据弹窗**（Tyche 会显示 Basic Auth 两项）；冷却 1800 秒，重填即清 |
| `ERR_CONNECTION_TIMED_OUT` / `ERR_CONNECTION_REFUSED` / `ERR_NAME_NOT_RESOLVED` 等 **14 个** Chromium 网络错误码 | `adapters/base.network_error_code()` 识别；抓取阶段命中就**终止本轮**（连不上没必要再登录一遍，省一次 5 秒预算 + 一次浏览器启停）并作为 error 条目上报 | 「无法连接到 Tyche（ERR_CONNECTION_TIMED_OUT）：该站点需要校园网/VPN。请连接校园 VPN 后点「刷新任务」重试。」 |
| 登录阶段的 `goto` 连不上 | `silent_login` 同样区分：网络错误 → `network_unreachable`（不再一律说成 `login_page_error`） | 同上那句话，不会被说成「登录页打不开」 |

**验证**：无表单（Basic Auth 未通过）→ 上报 `basic_auth_failed`、不再显示「登录页打不开，请检查网络」；抓取阶段网络错误 → **0 次登录**、提示含站点名与「校园 VPN」、不误报「需要登录」；真实网络指到本机没人监听的端口 → **0.8 秒**返回、`ERR_CONNECTION_REFUSED` 命中判类；不存在的域名 → **7.1 秒**返回、`ERR_NAME_NOT_RESOLVED` 命中判类；14 个错误码的正反例 → 命中正确、普通错误不误判。

### 3.5 Tyche 截止时间早 8 小时：接口给的是 UTC，且不带时区后缀

用户原话：**「我发现 tyche 里面 `startTime": "2026-10-11T16:00:00"` 是 2026-10-12 00:00，`endTime": "2026-10-18T15:59:00"` 是 2026-10-18 23:59」**（都是北京时间）。

**根因**：Tyche 的 `ShowGroup` 接口按 **UTC** 存时间，返回的字符串**既不带 `Z` 也不带偏移**。`adapters/tyche._extract()` 原实现只把 `T` 换成空格就透传，`task_logic.parse_time()` 于是把「没有时区信息」的时间**当成本机时间** —— 每个截止时间都早了 8 小时：作业本当周日 23:59 截止，界面显示 15:59，红窗提前 8 小时报警，倒计时与「还剩多久」全部错位。

这不是「UTC 就一定错」：`smartestu._iso_to_local()` 是靠 **`Z` 后缀**认出 UTC 的（它的接口返回 `...000Z`）；Tyche 不带后缀，所以旧代码没有任何线索能发现这件事。

| 输入（Tyche 原值） | 修复前（当本机时间） | 修复后（按 UTC 换算） |
|---|---|---|
| `2026-10-11T16:00:00` | `2026-10-11 16:00` | **`2026-10-12 00:00`** |
| `2026-10-18T15:59:00` | `2026-10-18 15:59` | **`2026-10-18 23:59`** |

**修法**：`adapters/base.py` 新增 `utc_iso_to_local()` —— **没有时区信息时一律按 UTC 解释**（naive 的 `astimezone()` 会假定它是本机时间，这正是这个 bug 的来源），再换算成本机时间文本；带 `Z` / `+08:00` 的输入不会被二次偏移；解析失败原样返回，交给 `parse_time` 兜底。`adapters/tyche._extract()` 的 `start` / `end` 改用它。

**验证**（本机时区 +0800）：

| 检查 | 结果 |
|---|---|
| 转换用例 | 上表两行逐项一致；`...000Z` → `23:00`；`+08:00` 原值不变；空值与非法值原样返回 |
| 端到端（报文 → `Homework` → 倒计时） | 北京时间 10-18 20:00 时，`hours_left` 由 **-4.02 小时（误判已过期）** 变为 **+3.98 小时** |
| 其他适配器排查 | `yuketang` / `unipus` 用毫秒时间戳（绝对时刻，本来就对）；`learn` / `thuoj` 取平台已格式化的本地时间 —— 全仓只有 Tyche 这一处是「不带后缀的 UTC」 |
| 冻结包 | 从 `PYZ-00.pyz` 取字节码复核：`adapters.base` 定义 `utc_iso_to_local`（含 `timezone` / `fromisoformat` / `astimezone`），`adapters.tyche` 已调用它 |

### 4.3 主题选择现在能记住：修「切了深色，再打开又变回跟随系统」

用户报障原话：**「怎么我现在切换成深色再打开还是变成跟随系统」**。

```python
cache_dir = tempfile.TemporaryDirectory().name    # 每次启动一个随机临时目录
```

窗口关闭时 `clear_user_data()` 再把整个目录 `rmtree`。结果：**运行期间切主题有效**（三个窗口还能靠 `storage` 事件实时同步），**但退出即清空** —— 下次启动 `theme-boot.js` 读不到键，按规则回落成 `auto`（跟随系统）。

**修法**：`webview.start(_after_start, private_mode=False, storage_path=<数据根>\webview)`。按 WebView2 官方建议把用户数据目录（UDF）放进应用自己的数据目录（与 `sites.yaml`、`data/` 同级；`paths.ROOT` 已保证可写，必要时已回退到 `%LOCALAPPDATA%\HomeworkTasks`），并关掉界面外壳的隐私模式。**两个实例共用同一 UDF 是官方支持的用法**（同一登录会话内共享一个浏览器进程），所以不引入新的多实例问题。关掉的只是**界面外壳**的隐私模式：抓取走 Playwright 与 `data/*_session.json`，完全不受影响。

**验证（前后对照实验：加载真实 `web/index.html`，窗口隐藏，两次独立进程）**：

| 配置 | 第 1 次运行（选「深色」） | 第 2 次运行（模拟重开程序） |
|---|---|---|
| 修改前（默认 private_mode，无 storage_path） | `localStorage = dark` | `localStorage = None`、`mode() = auto`、`<html data-lg-dark>` 不存在（**就是用户看到的现象**） |
| 修改后 | `localStorage = dark` | **`localStorage = dark`、`mode() = dark`、`<html data-lg-dark>` 存在** |

> **踩过的坑**：分析器第一版用 `(?<![\w.])` 作边界，会把 `_paths.ensure_dirs()` 排除在计数之外，以致把**在用**的 `ensure_dirs()` 报成死代码。修正边界后复跑为 0 处 —— 这类工具必须反向核对。

### 5.2 构建配方：不再把 Playwright 的源码当数据打进包

旧配方 `--collect-all playwright` 会把 Playwright 自己的 `.py` 源码当**数据文件**复制进包（63 个、1.38 MB，其中 `sync_api/_generated.py` 就 0.93 MB），还会生成本项目用不到的异步 API 字节码。新配方按类型精确收集：

```powershell
--collect-submodules playwright --collect-binaries playwright --collect-data playwright `
--exclude-module playwright.async_api
```

效果：包内 Playwright `.py` 源码 **63 → 0 个**，`playwright/async_api/` 不再生成。

## ⚠️ 行为变化（升级须知）

1. **首次运行会看到窗口**（以前是静默）。这不是「静默设置失效」—— 是出厂默认改成了「直接显示界面」，你在设置里打开「启动时静默」后照旧静默。
2. **首次运行不会去抓作业**：需要你先填至少一个站点的账号密码（或在设置里登录一次），之后一切照旧。
3. 升级后如果 `sites.yaml` 里**没有** `startup_mode` 键且你已有会话文件，行为**不变**（仍是静默）。
4. **首次出错要等一会儿**：抓取 + 一次真实登录合计约十几秒（实测 15.1 秒，其中判定密码错只占 2.1 秒，其余是浏览器启动/退出）；**之后再刷新是立即提示**（30 分钟冷却内不再登录）。
5. **慢站点会自己重登**：等满 5 秒（原来是 15 秒）仍没内容时，程序会丢弃该站点的登录记录、用你的账号密码静默重登一遍；重登失败或没有可用账密时才让你手动登录。
6. **任何抓取报错都会触发重登**（接口 500、页面改版也一样），但**只重登一遍**：判定结果约 2 秒时先播报到进度区，正式提示在十几秒内出现。没填账密与填错一样立即提示。重登前会先丢掉那份刚判失败的登录记录（否则会复用它空转三轮）。
7. **密码填错会立刻提示、不会反复登录**：平台明确回「用户名或密码不正确」时当场停下，显示「自动登录失败：账号或密码有误，请重新填写」（按钮：重新填写账号密码），30 分钟内不再自动登录。
8. **Tyche 的两类提示**：出现「Basic Auth 账号或密码有误，请重新填写」＝ 那一对 Basic Auth 凭据不对（点按钮即可重填）；出现「无法连接到 Tyche（错误码）：该站点需要校园网/VPN」＝ 这台机器连不到服务器，连上校园 VPN 后点「刷新任务」即可，程序不会再白跑一次自动登录。
9. **红窗会显示更早过期的任务**：取消 3 天下限后，几个月前就该交的未完成作业也会进红窗（排在靠前位置），白窗不再兜底它们。这是按需求改的，不是错乱。
10. **Tyche 的截止时间会整体后移 8 小时**：升级后 Tyche 作业的起止时间按 UTC 正确换算（原本显示 10-18 15:59 的，现在显示 10-18 23:59）。这是修错，不是作业数据变了 —— 之前红窗对 Tyche 会提前 8 小时报警。

## 📝 已知限制

1. **浏览器退出仍是固定开销（未解决）**：判定「密码错」只需 2.1 秒，但一次真实登录要 8.6 秒 —— 多出来的约 6.5 秒是 Playwright 退出浏览器的成本（`browser.close()` 本身 1.47s，慢的是整体退出；只有真正访问过网站的浏览器才这么慢）。要再压下去必须改浏览器生命周期（一次抓取共用驱动、或把退出移出关键路径）。现在的折中是「答案先播报、收尾继续跑」。
2. **慢站点会更频繁地触发真实重登**：数据窗口 5 秒 + 超时即重登，是用户明确选择的取舍（宁可自己重登一次，也不要停在「抓取超时」）。冷却机制是唯一的刹车。
3. **红窗排序副作用**：取消 3 天下限后，最陈旧的作业会排在红窗最前面（按过期时长升序），红窗一次最多显示 8 条。
4. **未做真实站点的端到端重登验证**：需要真实账号密码；超时/重登链路是用离线探针 + 真实网络的局部实测（Tyche、拒绝连接、域名不存在、挂死服务器）覆盖的。
5. **Tyche 的报错文字仍未收录**：现在靠「提交后停在表单」这条通用判据在约 3 秒给出结论；若将来拿到 Tyche 登录页的确切报错原句，可加进 `error_markers` 让它更直接。
6. **包体下限**：`node.exe` 89.24 MB 无法在不牺牲自动登录/抓取的前提下移除，50 MB 的 zip 已接近下限。
