## 🎯 为什么 v26.5 是界面上的转折点

前几个版本一直是在「能抓到什么」上做加法。v26.5 第一次动的是**眼睛能看到的那一层**，
而且改掉的不是配色好不好看，是三个结构性问题。

### 1. 三个窗口，终于只有一份主题表

主窗口、红色紧急浮窗、白色提醒浮窗是**三个独立的 HTML 文档**。浮窗读不到 `main.css` 的
`:root`，所以同一套颜色变量原先要在三个文件里各写一遍——70 个 token × 3 份 = 210 条声明
（含暗色层实际删掉 345 条）。

**改动前**：改一处颜色要记得同步三个文件，忘了就出这种事故——

- `--alert-mark` 只写在 `main.css` → 浮窗里解析成**空值**，红色标识直接消失
- `--ink` 的暗色值在主窗口调亮了，两个浮窗还是旧值，一直没人发现

**改动后**：新增 `web/theme-shared.css`，**只放 token，不放选择器与布局**。三个页面各自引入一次，
位置在**自己的样式表之前**，所以"某页特有的值"照旧能覆盖它：

```text
theme-boot.js → fonts.css → theme-shared.css → main.css / panel.css / alert.css
```

（三份 HTML 的引入顺序完全一致，`web/index.html:6-11`、`panel.html:6-10`、`alert.html:6-10`。）

共享表当前 **96 行 / 81 处 token 声明**；浅色与暗色各一套，暗色只覆盖需要变的那些。
同一轮里顺手清掉了 25 个零消费者的死变量（含它们互相引用的暗色别名），
以及三处因为"变量已搬到共享表"而过期的注释。

> 需要说清楚的是：**三份页面样式表里仍有大量字面色值**（`main.css` 413 处、
> `panel.css` 103 处、`alert.css` 97 处）。v26.5 解决的是"同一套 token 各写一遍"，
> 不是"所有颜色都 token 化"。把剩下的字面色值收敛是后续可以继续做的事。

### 2. 浅色 / 深色 / 跟随系统，三窗实时同步

**改动前**：没有主题概念，只有一套固定配色。
**改动后**：`web/theme-boot.js` 在 `<head>` 里同步执行（放在最前面，避免首帧闪色），
按 `localStorage['hwThemeMode']` 决定 `data-lg-dark` 是否存在：

| 模式 | 判定 |
|---|---|
| `auto`（默认） | `matchMedia('(prefers-color-scheme: dark)')`，并用 `change` 事件跟随系统实时切换 |
| `light` | 直接移除 `data-lg-dark` |
| `dark` | 设置 `data-lg-dark` |

跨窗口同步靠 `storage` 事件：同一个源（`file:///…/web/`）的窗口共享 `localStorage`，
任一窗口改主题，另外两个窗口会收到事件并立即重绘——**浮窗不需要重启也不会掉队**。
主窗口的设置面板「外观」里有三个按钮，切换结果即时生效。

### 3. 字体随程序走，且表单控件不再"漏"成 Arial

**改动前**：界面的中英混排依赖系统字体，按钮/输入框因为浏览器 UA 样式而用 Arial，一眼能看出不是一套。
**改动后**：`web/fonts.css` 用别名声明两款字体（`HW-Kai` 楷体_GB2312、`HW-Times` Times），
字体文件随包分发，离线可用、不发网络请求；`button, input, select, textarea` 统一 `font-family: inherit`。

这一轮还把字体体积做了减法：

| 项 | 改动前 | 改动后 |
|---|---|---|
| 字体文件 | 5 个 / 8,363,704 字节 | **3 个 / 6,496,636 字节** |
| 斜体面（TIMESI / TIMESBI） | 声明了，但全仓没有任何 `font-style: italic`，也没有 `<i>/<em>` 标签 | **删除**（省 1,867,068 字节） |

保留了 700 面（`TIMESBD.TTF`）：样式里有 12 处 `font-weight: 600`，按 CSS 字重匹配规则
会选中"≥600 的最近字重"，也就是这个 700 面——它并不是死文件。

> **同一版本内的后续更正：这一节已被推翻。** 上面那 3 个 `.ttf` 都是**商业字体**
> （两个 Times 面与本机 `C:\Windows\Fonts\times.ttf` 的 SHA256 完全相同），
> 随仓库公开再分发属于未授权使用。现在 `web/fonts.css` 只声明**系统字体**
> （`Times New Roman` → `KaiTi`/`楷体` → 华文楷体 → 微软雅黑 → 通用 serif，不再回退宋体），
> 仓库与安装包都不再包含任何字体文件（再省 6.2 MB）。观感不变：本机两套字体都在。

### 4. 进度文字"一条条出来"，而不是同一帧闪一下

**改动前**（`PROGRESS_BURST = 3`）：区域为空时前 3 行**立即输出**，于是那三行是同一帧里一起冒出来的，
看起来像一次闪烁，而不是"正在一条条抓"。
**改动后**：开场按 `PROGRESS_OPENING_DELAYS = (0.0, 0.28, 0.22)` 逐行放缓——第 1 行立即出，
第 2、3 行分别等 0.28 / 0.22 秒，之后收敛回常规节流 0.15 秒。

这里有一条硬约束被真正写进代码了：慢放在 `_progress_lock` 内 sleep，会顺带推迟并发 worker 的首行播报，
所以 `PROGRESS_OPENING_BUDGET = 0.5` 秒是**累计上限**，一到就不再慢放。
（之前这个常量只是注释里的承诺，没有任何代码执行它。）

### 5. 三个窗口的口径统一

- **倒计时**：以前浮窗在"不足 1 分钟"时统一显示「剩 1 分」，连已经过期的任务也显示「剩 1 分」；
  现在过期就说「已过期」、不足一分钟说「即将到期」，与主窗口一致。
  另外浮窗原先的"滑走"动画实际上永远看不见——后端在 `toggle_done` 返回前就重绘了列表，
  动画跑在已被替换的游离节点上，用户看到的是"瞬移消失"；这一轮删掉了那段无效动画。
- **行数上限**：主窗口进度区最多 3 行，红色浮窗最多 8 条、白色浮窗最多 12 条，超出的显示「…还有 N 条」。
- **加载失败**：主窗口首轮加载失败时，以前是"错误横幅 + 一片空白 + 计数 0"，
  无法区分"没有任务"和"没加载出来"；现在会给出明确的「加载失败」空态和重试提示
  （仅在列表本来就为空时清屏，不会把上一轮还能用的列表冲掉）。
- **状态刷新**：60 秒定时器以前只更新剩余时间文字，任务跨过 24 小时阈值后颜色不变；
  现在会同步重算"紧急/已过期"状态。

## 🔐 重大改进一：登录失败的原因不再丢失

这是本轮"性价比最高"的一类修复：**程序知道原因，但没告诉用户**。

**改动前**：`Api.login()` 只返回 `{"ok": ok}`。前端明明备好了五套话术，却永远用不上，
失败时统一显示「登录未完成，点击重试」。于是：

- 密码真的错了 → 用户反复点同一个按钮，反复拉起真实 Edge 窗口
- 其实只差一次验证码 → 同上
- 平台根本不支持自动登录（雨课堂）→ 同上

**改动后**：原因沿整条链路透传，后端 `login_site()` 返回 `(ok, reason)` →
`Api.login()` 返回 `{"ok":…, "reason":…}` → 前端按原因给话术与动作：

| 原因 | 界面怎么说 | 按钮做什么 |
|---|---|---|
| `bad_credentials` | 账号或密码可能不对，请点按钮重新填写 | 打开**凭据弹窗** |
| `no_credentials` | 未填账号密码，无法自动登录 | 打开**凭据弹窗** |
| `mfa` / `manual_required` | 需要你确认一次验证码 | 拉起登录窗口（账号密码已预填） |
| `session_unstable` | 登录成功了但会话没能保存下来 | 重试登录 |
| `no_adapter_support` | 该平台不支持自动登录 | 手动登录 |
| `timeout` / `exception` / `login_page_error` | 超时 / 出错 / 登录页打不开 | 重试登录 |

配套修掉的三个"把用户引向错误动作"的问题：

1. **二次验证被误判成密码错**。判定顺序反了——先扫正文里的「登录失败」「无法登录」这类泛化短语，
   再看二次验证界面。真 MFA 页面（帮助文案里就有这些词）会被判成 `bad_credentials`，
   冷却从 300 秒变 1800 秒，还引导用户去改一个**正确的**密码。
   现在**二次验证判定排在正文扫描之前**，且正文扫描只认足够独特的长句（`无法登录`/`登录失败` 已从判据中移除）。
2. **选学校失败被说成密码错**。数你最灵的选校选择器改版时，程序仍会填账号密码并提交，
   服务端回"用户名或密码错误" → 报 `bad_credentials` → 30 分钟冷却 + 引导改密码。
   现在选校失败会被记为独立原因，失败时按「选校失败」上报，不再套用密码错的话术与冷却。
3. **更强的失败原因被更弱的覆盖**。无头层已明确得到 `bad_credentials`，屏幕外层因为慢给出 `timeout` 时，
   原先直接用 `timeout` 覆盖（冷却 1800→300 秒、话术退化成"去确认验证码"，于是每 5 分钟再撞一次 SSO）。
   现在按"原因强度"保留更能说明问题的那个。

**完全没变的是**：上面三层登录尝试、冷却时长、屏幕外窗口策略，都与 v26.4 一致。

## 🛡️ 重大改进二：不会再丢配置

### 1. 读不出配置时，拒绝写入

`_read_config()` 以前在**读失败**和**文件不存在**两种情况下都返回 `{}`。而
`save_startup_mode()` / `apply_sites_changes()` 拿这个 `{}` 当"完整配置"、补一个键就原子写回——

**后果**：`sites.yaml` 因为被同步工具占用（`PermissionError`）或手工存成了非 UTF-8（`UnicodeDecodeError`）
而读失败、且备份也不可用时，用户在「设置 → 启动行为」点一下开关，写回的内容就只有
`{startup_mode: …}` 一个键：**六个站点的配置连同里面的密文账密一次性消失，而界面显示"已保存"。**

**改动后**：`_read_config(strict=True)` 区分"不存在（返回 `{}`，首次启动的正常情况）"与
"读不出来（抛 `ConfigUnreadable`，写路径必须处理）"。写路径收到异常时返回错误、
**拒绝写入**，前端会显示"应用失败：拒绝写入（读不到现有配置，写了会丢数据）…"。
只读路径（读启动行为）仍然退回默认值，不会因此报错。

### 2. 配置坏掉时，界面不再显示"所有任务都已完成，太棒了！"

`load_sites()` 解析失败时返回空列表，与"真的没有站点/没有作业"完全无法区分。
用户手工编辑 `sites.yaml` 写坏 YAML、又没有可用备份时，看到的是空态文案 + 计数 0 + **一条横幅都没有**，
而且程序永不重建模板（文件存在）。

**改动后**：读失败的原因会传到界面，显示为一条明确的错误横幅：

> `sites.yaml 无法解析（…），且没有可用的备份。本次没有可抓取的站点。
> 请修好该文件，或先把它改名/删除，程序会按 sites.yaml.template 重新生成一份。`

### 3. 「读—改—写」不再互相覆盖

`save_site_credentials` / `apply_sites_changes` / `save_startup_mode` 都是
"读全量 → 改内存 → 整体写回"两段式，中间没有锁。pywebview 给**每一次** js_api 调用起一个独立线程
（`webview/util.py` 里就是 `Thread(target=_call)`），所以两个调用真的会重叠：
后完成者用旧快照整体覆盖，前一次改动无声消失——而**两次都返回 `{"ok": True}`**。

**改动后**：新增 `config_transaction()`（`_config_rw_lock`），把整段读-改-写串行化，
锁序固定为 `_config_rw_lock → _sites_lock`，不反向持有。

### 4. 明文升级失败不再假装成功

`upgrade_plaintext_credentials()` 的 `try: save_sites(...) except` 里的 `except` 是**死代码**
——`save_sites` 只返回 `(ok, err)`，从不抛异常。于是写盘失败时既不记日志也不回头，
仍然打印"已把 N 个明文账号/密码升级为加密存储"，而磁盘上还是明文。

**改动后**：显式判 `(ok, err)`；单字段加密失败也会被记下来（该字段会随整文件写回磁盘，
也就是明文留在磁盘上）。这类问题在窗口化 exe 下 `print` 是看不见的，所以它会被顶到界面上：

> 账号密码加密升级失败，磁盘上可能仍是明文。

## ⚡ 重大改进三：网络故障不再被说成"未登录"，失败不再变成"0 条"

同一个事实（接口没给出数据）在不同适配器里有三种相反的解释，用户被引向三种不同的动作。
这一轮统一成三分类：**没登录 ≠ 抓取失败 ≠ 没有作业**。

| 站点 | 改动前 | 改动后 |
|---|---|---|
| Tyche | 接口 500 或网络抖动一律抛"需要登录" | HTTP 401/403 → 需要登录；5xx / 网络错误 → **抓取失败**（不再触发无意义重登） |
| U 校园 | 同上 | 同上（区分 401/403 与 5xx/网络异常） |
| 雨课堂 | 未登录时接口 401 被当成"课程为空"，永远显示「完成 0 条」，等不到扫码提示 | 401/403 → **需要登录**；课程接口失败 → 抓取失败 |
| 网络学堂 | 丢弃了已拿到的 `httpStatus`，401/500 的错误页被 `json.loads` 静默吞掉 → 「完成 0 条」，既不进 errors 也不重登 | 401/403 → 需要登录；所有课都拿不到可用响应 → **抓取失败**（部分成功则保留成功部分并记录） |
| 数你最灵 | 接口 `success:false` 直接返回空列表；且"有效会话但没有课程"被判成未登录（白等 20 秒 + 引导去确认验证码） | 接口失败按"会话是否有效"分流；"已登录但没选课"返回 0 条，不再报未登录 |
| 网络学堂课程缓存 | 读缓存**没有 try**，写缓存**不是原子写**（全仓唯一一处绕过原子写的数据直写）。缓存在写盘中断后损坏，则**每次刷新**都在 `json.load` 抛错，且不会自愈 | 读失败丢弃坏缓存并重建；写走原子写 |

另外修掉两处"抓了就丢"的诊断：

- **会话文件损坏的自愈分支会把真实异常完全吞掉**（选择器失效、接口 500、Playwright 崩都走这里）。
  现在至少留一行 `print`，并把最近若干行静默登录诊断（有界内存环形缓冲，**不写日志文件**——
  历史上曾因日志自反馈涨到 194GB）附在"需要登录"条目的 `detail` 上，随界面展示。
  窗口化 exe 下 `sys.stdout` 是 None，这是唯一能让用户看到原因的出口。
- **手动「刷新任务」也会先等网络 120 秒**，还被 `_fetch_lock` 串行化（连点两次最长等 240 秒，
  很像"刷新按钮卡死"）。文档承诺的一直只是"**启动时**最多等待 120 秒"——
  现在改成只在进程首轮抓取时等待，并且**等待前先播一行"检查网络…"**，不再空白 120 秒。

## ⏱️ 截止时间解析与列表顺序

`core/task_logic.py` 是纯函数，这轮用一个探针把它的边界实测了一遍。

**改动前**：

```text
parse_time(1735689600000)              -> AttributeError: 'int' object has no attribute 'strip'
parse_time('2026/1/2')                 -> None
parse_time('2026-1-2')                 -> None
parse_time('2026-01-02 03:04:05.123')  -> None
parse_time('2026-01-02 03:04:05+08:00') -> None
```

**改动后**：数字与 9 位以上纯数字字符串按时间戳解析（13 位按毫秒）；支持小数秒、时区偏移、`Z`、
非零填充的月/日；带时区的值先换算成本机时区再比（否则带 tzinfo 与 naive 的 `now` 相减会直接抛 `TypeError`
——那会把"没有倒计时"升级成"整轮渲染崩掉"）；非字符串非数字的输入返回 `None` 而不是抛异常。

列表分类也修了两处：

- **过期任务永久霸占红窗**：`compute_urgent` 只有上界（`<= 24h`）没有下界，
  一年多前就该交的作业永远排在红窗第 1 位（红窗只显示 8 条），把真正 24 小时内到期的挤下去，
  而且因为它被算作"紧急"，白窗里也看不到。现在红窗只保留**最近 3 天内过期**到 24 小时内到期的任务，
  更早的降级到白窗——**是降级，不是删除**，忘交的作业仍然看得见。
  > **第二批已按需求取消这个 3 天下限**：现在过期多久都算紧急，见文末《第二批》第 8 条。
- **列表顺序自己跳**：`compute_normal` 只按截止时间字符串排序，而 `end` 相同（很常见，都是 23:59）
  或为空时（都映射成 `"9999"`）顺序完全取决于并行抓取的完成顺序。现在加了次级键 `uid`，同分项顺序稳定。

## 📝 已知限制

这些是本轮**有意没有改**的，写在这里避免下次又被当成新发现：

- **手动登录期间刷新会被拖住**：点「登录」后慢慢过验证码时，该站点锁最多被持有 600 秒，
  此时点「刷新任务」会等它——因为另一种做法（跳过该站点）会让这个站点的任务从列表里消失，
  用户会以为任务丢了。要改需要先设计"跳过但保留旧数据"的语义。
- **关闭主窗口时若正在抓取**：解释器退出会 join 抓取线程，进程可能停留数十秒（"关了还在跑"）。
  已实测确认机制，但没有改成阻塞式等待（那会让"点 X 就该立刻退出"更糟）。
- **两条路径目前不可达**：适配器的 `manual=False` 分支（静默登录实际由 `auto_relogin_site` 直接调用）、
  `interactive_login(keep_alive=True)`（为"让用户指认元素"预留，当前无调用方）。属于扩展位，未删。
- **没有单实例保护**：双开（开机自启 + 手动打开）时两个进程会写同一个数据库与配置临时文件，
  由 `os.replace` 原子替换与 SQLite 忙等兜住，但没有命名互斥体。
- **配置读取仍以"文件存在"为准**：文件内容坏掉时不会自动重建模板（避免覆盖用户数据），
  而是给出横幅让用户自己决定。
- **雨课堂仍然只支持扫码**：这是产品上的有意豁免，不是缺陷。能力位
  `SUPPORTS_SILENT_LOGIN = False` 已经把这件事实收敛到一处，新增平台时只要不写这个常量就默认支持。
- 三份页面样式表里仍有大量字面色值（见上文），token 化只完成了一部分。

## 🧩 第二批：首启闸门、启动行为与失败处置

> 这一批与上文同属 **v26.5**。原稿独立成文时误记为「v26.6」，内容、结论与验证都不变，仅版本标识归位。

### 🎯 这一批要解决的问题

用户反馈的原话是：「exe 等待时间太长了，要不要加一个检测是否有数据文件，如果没有就马上弹出窗口并且不进行数据刷新，在账号密码填写好后进行正常行为。」

这句话指向的是一个真实且可复现的体验问题。首次运行（或在一台干净的机器上首次运行）时：

- `data/` 里没有任何 `*_session.json`；
- `sites.yaml` 里的账号密码还是空的（模板就是空串）。

程序却照样走完整流程：

1. `wait_for_network(timeout=120)` —— 没网/网络慢时**白等最多 120 秒**，这是启动路径上唯一会播报文字、也是唯一会在最前面阻塞的一步；
2. 为**每个**启用站点拉起一个 Playwright 浏览器去「抓作业」，而每个站点都要等登录页超时才放弃（数秒到数十秒）；
3. 结果必然是「需要登录」——用户等了半分钟到两分钟，等到的是一条本来一开始就能告诉他的提示。

而且默认启动行为是「静默」，所以**等的时候连窗口都没有**：用户看到的是"双击以后很久什么都没发生"。

---

### 🚀 主要改进

#### 1. 首启闸门：没有数据文件就不抓，直接显示窗口

判定口径（与用户逐条确认过）：

> **没有任何可用会话文件，且没有任何站点填了能解密出来的账号密码** → 这一轮不发任何网络请求、不启动浏览器，立即显示主窗口，并给出「去填账号密码」的引导。

只要还有**任意一个**启用站点存在会话文件、或填了可用账密（下次能静默登录），就完全按原来的流程正常抓取。

实现位置：

- `core/site_runner.py`：`startup_gate()` 是唯一判定入口，配 `data_file_present()` / `_site_has_usable_session()` / `_site_has_credentials()` / `_site_credentials_broken()` 几个小函数；
- `core/controller.py`：`Api.get_homeworks()` 在**调用 `fetch_all()` 之前**先问一次闸门；命中就直接返回 `{"gate": {...}}`。

命中闸门时做了什么、**没做**什么（有断言脚本逐条覆盖）：

| | 行为 |
|---|---|
| 网络等待 | **不执行**（`wait_for_network` 调用次数 = 0） |
| 站点抓取 / 浏览器 | **不执行**（`fetch_all` 调用次数 = 0） |
| 后台重登 | **不执行**（`auto_relogin_site` 调用次数 = 0） |
| 窗口 | 立即 `show_main_window()`，**静默档也显示** |
| 任务数据 | **不清缓存**；缓存里的站点任务 + `homework.db` 的手动任务照常返回 |
| 首轮网络等待 | 复位成「还没等过」，留给用户填完账号密码后的第一次真正抓取 |

#### 2. 「静默」改回默认关：它该是用户的选择，不是默认值

- 旧默认：`STARTUP_MODE_DEFAULT = "silent"`，模板也写死 `startup_mode: silent`。
  后果是**第一次运行的人什么都没看见**——而这时他恰恰最需要看见窗口。
- 新默认：`visible`。`sites.yaml.template` 同步改成 `startup_mode: visible` 并更新了注释。
- **兼容**：配置里没有 `startup_mode` 这个键时，按「有没有数据文件」区分——
  - 已经有会话文件（老用户，程序在他机器上正常用过）→ 沿用 `silent`，**升级不改变既有行为**；
  - 一个会话文件都没有（全新机器，他从未做过这个选择）→ `visible`。
- 一旦用户在设置里动过这个开关，`sites.yaml` 里就有了这个键，之后一律以用户的值为准。

#### 3. 引导条与空态：不让"没有数据"看起来像"没有作业"

命中闸门时主窗口顶部显示一条引导（`.banner.setup`）：

- 一句说清现在是什么状态（"这是第一次运行：还没有任何登录状态…"）；
- 三步下一步：① 点站点按钮填账号密码（雨课堂只能扫码，先不用管）② 填完自动开始抓取 ③ 只想手动记作业就直接「添加任务」；
- 每个待配置站点一行按钮，按钮文案/话术复用既有的 `LOGIN_HINTS`（不新增第二套话术表）；
- 一个「打开设置」按钮。

同时任务列表的空态也不再借用绿色那句「所有任务都已完成，太棒了！」——
首次运行时列表为空**不是**"没事可做"，而是"还没登录"。这句话以前会把用户误导成"程序已经没事干了"。

#### 4. 顺手修掉的两处既有问题

- **手动任务曾经会丢**：短路分支如果直接返回 `_items_cache`，用户上次会话里加过的手动任务（只存在 `homework.db`，不在缓存里）就会凭空消失。现在短路与正常路径共用 `_merge_cached()`，都从 DB 读手动任务。
  这条在实现过程中被独立核验抓到过一个更隐蔽的变体，值得记下来：
  **短路分支只读缓存、却不写回缓存**，而 `add_task` / `toggle_done` / `delete_task` 结尾的 `_sync_main()` 是拿 `_items_cache` **整体覆盖**前端列表的。
  于是纯手动任务用户（引导条推荐的用法之一）勾一下复选框，列表当场被刷空（DB 里其实还在），再点刷新还会出现一条重复行 —— 缓存与返回值不一致，比"数据丢了"更像"程序坏了"。
  现在短路分支返回前会把合并结果写回 `_items_cache`，`_merge_cached()` 也做成**幂等**（按 uid 去重、保留 `manual` 标记），正常路径同样受益。
- **抓取结果没有去重**：适配器把同一个作业从两个入口返回时，列表里会出现两行。正常路径现在按 `uid` 去重（uid 为空的条目不参与，避免把本来不同的作业合成一条）。

#### 5. 闸门自己出错时不许吞掉抓取
`startup_gate()` 的定位是"少做一次注定失败的抓取"，所以它**任何一步出问题都必须放行**：
- 配置读不出来（`config_error()`）→ 不短路，交给 `fetch_all()` 报"配置坏了"，用户不会看到"没有任务"的假象；
- 站点级判断抛异常（例如 `adapters.auth` 导入失败、DPAPI 解密整体异常）→ 不短路。
  `_site_has_credentials()` 因此返回**三态** `True/False/None`：`None` 表示"判断不出来"。
  早期实现里异常被吞成 `False`，所有站点都会看起来"没填账密"，闸门就会把一轮本该执行的抓取吞掉 —— 这是 fail-closed，方向反了。

#### 6. 会话预检提速：15 秒 → 1 秒（第二项需求）

用户反馈："等待过去会话是否可复用是否要填账密的时间太长了，要 15s，改成 5s 吧"。

先量了一下，发现**那 15 秒全是干等**：无头请求实测 `learn` 首页 0.10 秒返回，而且最终 URL
**已经变成 `/f/login`**（会话失效时浏览器是被服务端直接跳到登录页的）。
代码却在校验"作业列表出现没有"—— 这个条件在登录页上永远不会成立，所以只能把 15 秒睡满。

改动（`adapters/auth.py` + 5 个适配器）：

- 新增 `page_on_login_page()`，并在 `wait_for_ready()` 的每轮轮询里检查：
  **一确认页面在登录页/认证页上就立即结束等待**，不再睡满；
- `SESSION_PROBE_MS = 1000`（会话预检上限）、`DATA_READY_MS = 15000`（数据就绪）；
- 5 个适配器（learn / thuoj / unipus / tyche / smartestu）的 `15000`（smartestu 是 `20000`）
  拆成"预检 1 秒 + 必要时数据 15 秒"两段，并去掉超时后那段固定补等待
  （learn 3 秒 / thuoj 2 秒 / smartestu 2 秒 —— 慢页面已由数据时限覆盖，补等待只拖慢"会话失效"这条路径）。

**为什么数据那段反而从 15 秒改回来、不再往下压**：超时值以前同时承担了两件事——
"会话还有没有用"和"数据来没来"。现在前者由早退负责，后者才是超时该管的，
所以超时**不需要**卡得很紧；反倒是卡得越紧，越容易把"慢"误判成"失效"。

> **同一版本内的后续更正**：这个"不再往下压"的结论被用户推翻了 ——
> 用户要求把数据等待从 15 秒改成 **5 秒**（`DATA_READY_MS = 5000`），并且超时后
> 不再只报错、而是自动清登录记录并静默重登一次（见文末第 9 条）。也正因为超时
> 现在会触发真实重登，"卡得越紧越容易误伤"这个权衡变得更敏感：慢站点会更频繁地
> 走一次真实的重新登录。

#### 7. 超时不再等于"去重新登录"（这条才是根因）

> **⚠️ 同一版本内的后续更正（本节结论已被反转）**：用户随后明确要求
> "把慢的网站也别直接报错了，超时之后就自动清除登录记录重新登陆"。现在超时
> （`FetchFailedError.timeout=True`）会**清掉该站点登录记录并静默重登一次**，
> 见文末第 9 条。本节保留的是"当初为什么没那么做"的推理过程，下面的表格、文案
> 与底账都以第 9 条为准；历史叙述不改写。

改动 6 之后还剩一个更根本的问题。原来的判定是：

```text
预检超时 → 判 _is_logged_in() == False → raise LoginRequiredError
                                          → 触发后台静默重登（每站 10~60 秒，还可能弹窗）
```

而 `_is_logged_in()` / `_on_logged_in_page()` 返回 False 有**两种**原因：
"会话真失效"和"页面根本没来得及加载"。超时属于后者，却被当成了前者 ——
所以**任何**超时值都会误伤慢站点，把 15 改成 8 只是换个概率。

现在按"信号强度"分流（`adapters/*.py`）：

| 现象 | 判定 | 后果 |
|---|---|---|
| 页面明确跳到登录页 / SSO 页 | `LoginRequiredError` | 该重登就重登（且通常 1 秒内就判出来） |
| 接口明确 401 / 403 | `LoginRequiredError` | 同上（unipus / tyche / smartestu 的接口都是硬信号） |
| 等了 `DATA_READY_MS` 仍没内容、又**没有任何**失效信号 | `FetchFailedError(timeout=True)` | 当时：报"抓取超时"、**不触发重登**（**已被第 9、10 条反转**：现在任何报错都重登，最多连续 3 次；超时先清登录记录） |

文案由 `auth.timeout_detail()` 统一给（5 个站点共用一句，不各写一遍）：

> 「网络学堂页面 在 15 秒内没有返回内容。可能是网络或平台较慢，也可能登录状态已失效 ——
> 如果点「刷新任务」重试仍不行，请点「登录」重新登录一次。」

两头都说，是因为这种超时**真的判不出来**：说"你要重新登录"会把慢站点引去做一次白重登；
说"没问题"则万一是真失效，用户就没有出口。

> ⚠️ 这里必须留个底账：`FetchFailedError` 在 `site_runner._fetch_one_site_locked` 里
> 走的是"只播报错误"分支（`except Exception`），**不会**触发 `auto_relogin_site`。
> 这是刻意的，也正是这条改动的意义所在。

**为什么敢把预检压到 1 秒**：只有当"页面确实在登录页上"时才提前结束，
所以"页面只是慢"不会被误判成会话失效；而一旦误判就会触发一次白跑的重登（更慢、还可能弹窗）。
这也是必须给数据阶段留足 15 秒的原因。

**实测（真实无头 Edge，同一个空会话文件）**：

| | 改动前 | 改动后 |
|---|---|---|
| 等待部分 | 19.1s（15s 超时 + 3s 补等待 + 约 1s 导航） | **0.69s**（预检命中登录页，当场返回） |
| 端到端（`learn.fetch_homeworks`） | 约 26s | 7.27s |

**为什么端到端还剩 7 秒 —— 一个必须说清的发现**：其中约 **6.5 秒是 `browser_session`
退出时关浏览器的固定成本**，与本次改动无关：

```text
只启动不干活            退出 0.65s
about:blank + context  退出 0.63s
真实访问过网络学堂       退出 6.96s   ← 只有真的访问过网站才慢
直接调 browser.close()  1.47s        ← 慢的不是 close 本身，是 playwright 整体退出
```

也就是说，"每次抓取固定约 7 秒、与站点和网络无关"的这笔开销仍然存在，
它不在这条 15 秒超时里，属于另一个问题（若要继续提速，应从"浏览器生命周期"下手，
例如一次抓取共用浏览器或把退出移出关键路径）。

#### 8. 红窗取消"过期 3 天"下限：过期多久都算紧急（用户要求）

第一批给红窗加过一个下限 `URGENT_PAST_GRACE_HOURS = 72`（过期超过 3 天的降级到白窗）。
**用户明确要求取消它**，所以：

- `core/task_logic.py` 删掉该常量，`compute_urgent` 只判上界：未完成、`end` 能解析、
  `hours_left <= 24` 就进红窗，**包括已经过期任意久的任务**；文件头注释保留了这段历史。
- 已知副作用（用户已知悉并接受）：列表按 `hours_left` 升序，过期越久越靠前，
  所以最陈旧的作业会出现在红窗最上面几行；红窗一次最多显示 8 条。
- 文档同步：README 的功能列表与「红色浮窗没有显示？」一问都改成了"所有已过期都算紧急"。

#### 9. 超时后自动清除登录记录并静默重登（用户要求，反转第 7 条）+ 数据等待 15 秒 → 5 秒

用户需求原文两句：

> 「把慢的网站也别直接报错了，超时之后就自动清除登录记录重新登陆」
> 「而且把 15s 改成 5s」

**判定层**（`adapters/base.py`）：`FetchFailedError` 新增 `timeout` 标记，
只有"等满 `DATA_READY_MS` 仍没内容、又**没有任何**失效信号"这一类才置 `timeout=True`
（6 个抛出点：learn / thuoj / tyche / unipus / smartestu ×2）。接口 5xx、页面结构变化
仍然是 `timeout=False`。

**处置层**（`core/site_runner.py`）：`_should_relogin_after_timeout()` 决定要不要
"清登录记录 + 重登"，四个条件缺一不可：

| 条件 | 为什么必须 |
|---|---|
| `exc.timeout is True` | 5xx / 结构变化不代表会话失效，不拿用户的登录状态去赌 |
| 平台支持账密自动登录 | 雨课堂只能扫码，清掉会话等于把用户踢下线 |
| 有可用账密 | 没有账密就登不回来，报一条错误比"变成需要登录"更好 |
| 账密能在本机解密 | 换了电脑 / 换了 Windows 账户时密文解不开，同样登不回来 |

命中则 `_discard_session(reason=…)` 清掉会话文件，然后走**已有的**静默重登分支：
重登成功 → 立刻重新抓一次；失败 → 照旧给出 `need_login` 与原因话术。
`_discard_session()` 的日志文案改成由调用方传 `reason`，免得在超时路径上
说"会话文件损坏"这种假话。

**时间**（`adapters/auth.py`）：`DATA_READY_MS = 5000`（原 15000），
`wait_for_ready()` 的默认值同步改成 5 秒；`timeout_detail()` 的文案现在说的是
"在 5 秒内没有返回内容"，也不再声称"程序不会自动重登"。

**代价（必须说清楚）**：数据窗口 15 秒 → 5 秒、且超时即重登，意味着**慢站点更容易
触发一次真实的重新登录**（每站 10~60 秒，清华 SSO 还可能弹窗）。这是用户明确选择的
取舍：宁可让它自己重登一次，也不要停在"抓取超时"上。

**本条的验证**（离线探针，18 条断言全过；断言脚本按项目惯例不入库）：
超时+有账密 → 会话被清、重登 1 次、重试成功（2 次 fetch、1 条、0 报错）；
接口 500 → 不重登、会话保留、照常报错；超时但没账密 → 不重登、会话保留；
超时但平台不支持账密登录 → 不重登、会话保留；超时但账密解不开 → 不重登、会话保留；
`DATA_READY_MS == 5000` 且超时文案为 5 秒。**未**用真实站点做端到端（需要真实账密）。

> 第 10 条把这里的"只对超时重登"放宽成了"任何报错都重登"，清登录记录仍只对超时。

#### 10. 任何报错都尝试重登，最多连续 3 次（用户要求，进一步反转第 7 条）

用户要求原文：

> 「不要，只要报错什么就尝试重登，最多连续重登三次」

**规则**（`core/site_runner._fetch_one_site_locked` 改写成"抓取 → 失败则重登 → 再抓"
的有界循环）：

| 失败类型 | 重登前是否清登录记录 | 之后 |
|---|---|---|
| 页面跳登录页 / 接口 401、403（`LoginRequiredError`） | 不清 | 重登；失败则提示"需要登录" |
| 会话文件损坏 | 清（自愈，原有行为） | 重登；失败则提示"需要登录" |
| 超时（`FetchFailedError.timeout=True`） | **清** | 重登；失败则报"抓取超时" |
| 接口 5xx / 页面改版 / Playwright 崩溃 | 不清 | **也重登**；失败则照实报错 |

循环上限 `RELOGIN_MAX_CONSECUTIVE = 3`：一次刷新里最多连续重登 3 次（最多 4 次抓取）。
上限是必需的 —— `auto_relogin_site()` 在**登录成功**时会清掉冷却，如果平台一直 5xx，
"报错 → 重登 → 再报错"会无限转下去，一次刷新就卡死了。`auto_relogin_site()` 自己
仍然拦三种情况：平台不支持账密登录、没有可用账密、刚失败过的冷却期
（需要验证码 10 分钟 / 账密不对 30 分钟）。

**代价（必须说清楚）**：这是最激进的一档 —— 接口 500 也会触发真实重登
（每站 10~60 秒，清华 SSO 可能弹窗），最坏情况一个站点在一次刷新里要花掉三次登录的
时间。这是用户明确选择的取舍：宁可反复重登，也不要停在报错上；冷却机制是唯一的刹车。

**本条验证**（离线探针，13 条断言全过；脚本按项目惯例不入库）：

| 场景 | 期望 | 实测 |
|---|---|---|
| 500 + 有账密，重登一次后抓取成功 | 重登 1 次、抓 2 次、无报错、**不清**会话 | ✓ |
| 一直 500，重登一直成功 | 正好重登 3 次、抓 4 次，最后照实报错 | ✓ |
| 超时 | 重登前**已清**会话；重登后抓取成功 | ✓ |
| 需要登录 + 重登成功 | 抓到数据，既不报错也不提示 | ✓ |
| 需要登录 + 登不回来 | `need_login=1`、`errors=0` | ✓ |
| 没有账密 | 只抓 1 次、直接报错，不进重登循环 | ✓ |
| 重登返回 False（冷却中） | 立刻收手，不再抓 | ✓ |

### ⚠️ 行为变化（升级须知）


1. **首次运行会看到窗口**（以前是静默）。这不是"静默设置失效"——是出厂默认改成了"直接显示界面"，你在设置里打开「启动时静默」后照旧静默。
2. **首次运行不会去抓作业**：需要你先填至少一个站点的账号密码（或在设置里登录一次），之后一切照旧。
3. 升级后如果 `sites.yaml` 里**没有** `startup_mode` 键且你已有会话文件，行为**不变**（仍是静默）。
4. **红窗会显示更早过期的任务**：取消 3 天下限后，几个月前就该交的未完成作业也会进红窗
   （排在红窗靠前位置），白窗不再兜底它们。这是按需求改的，不是错乱。
5. **慢站点会自己重登**：等满 5 秒（原来是 15 秒）仍没内容时，程序会清掉该站点的
   登录记录、用你的账号密码静默重登；重登失败或没有可用账密时才会让你手动登录。
6. **任何抓取报错都会触发重登**（接口 500、页面改版也一样），一次刷新最多连续重登 3 次，
   所以出错时界面会多停留几十秒到几分钟。只有"超时"会清登录记录，5xx 不会。
