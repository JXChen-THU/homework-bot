## 🚀 v26.4 主要改进

### 1. 有账号密码就自动后台登录

**改动前**：所有平台都靠首次手动登录并保存会话；会话过期后必须由用户手动点「登录」按钮，
弹出浏览器窗口手动操作。

**改动后**：在设置里填好账号密码后，抓取时一旦发现登录状态失效，
程序会在**后台无头浏览器**里自动重新登录，成功后立刻重抓，用户完全无感。

新增 `adapters/auth.py` 作为静默登录公共设施：每个适配器只提供
`LOGIN`（登录页、选择器、提交方式）和 `is_logged_in(page, site)`（登录成功判定），
由 `silent_login()` 统一驱动；`interactive_login()` 负责需要人工介入的场景。

调度层 `core/site_runner.fetch_all()` 的流程变为：

1. 正常抓取
2. 抛 `LoginRequiredError` → 有账号密码就 `silent_login()`
3. 静默登录成功 → 立刻重抓
4. 仍然失败 → 报告给前端，并带上失败原因（`no_credentials` / `qr_code` / `manual_required`）

### 2. 各平台实测结论

本次实现前逐个平台做了实测（无头浏览器 + 真实账号），结论如下：

| 平台 | 登录方式 | 自动后台登录 | 备注 |
|---|---|---|---|
| Tyche | Basic Auth + 网站表单 | ✅ 完全自动 | `#username` / `#password` |
| 数你最灵 | 学校 + 学号/工号 + 密码 | ✅ 完全自动 | 必须先选学校 |
| U 校园 | 手机号/邮箱 + 密码 | ✅ 完全自动 | 首页「登录」→ `/portal/sso/login` |
| 网络学堂 | 清华统一身份认证 | ✅ 屏幕外窗口 | 无头会被挑战，真实窗口放行 |
| 清华 OJ | 清华统一身份认证 | ✅ 屏幕外窗口 | 本地表单接口返回 500，只能走 SSO |
| 雨课堂 | 微信扫码 | ❌ 不支持 | 扫码无法自动化 |

**关键发现：决定因素是「有真实窗口」而不是「可见」**

一开始以为清华 SSO 是在「无头 vs 可见」之间区分，于是做了对照实验：

| 方式 | 结果 |
|---|---|
| 无头、全新上下文 | ❌ 被要求二次验证 |
| headed、窗口放在屏幕外 `(-32000,-32000)` | ✅ 直接登录成功 |
| headed 屏幕外 + CDP 最小化 | ✅ 直接登录成功 |

结论：SSO 挑战的是**无头浏览器**，真实窗口即使完全不在屏幕上也会被放行。
因此只要开一个真实窗口并把它移到屏幕坐标之外，就能做到「用户完全看不见、
但登录照常成功」。这就是第二层的由来。

> 为什么不用「最小化」：窗口必须先创建出来才能最小化，
> 创建那一瞬间仍会在屏幕中央闪一下。屏幕外位置是在创建时就指定的，
> 全程不会出现在可见区域。代价是任务栏上可能短暂出现一个图标（已实测，可接受）。

**跳过注定失败的无头尝试**：既然清华两个站的无头登录**必定**被要求二次验证
（多次实测稳定复现），就没有必要每次都先跑一遍。适配器用
`LOGIN["skip_headless"] = True` 声明这一点，调度层对该站点直接走屏幕外窗口。
收益：每站省约 10 秒，也少一次多余的 SSO 交互（降低触发风控的概率）。


### 3. 清华 OJ / 网络学堂 的登录入口

- 网络学堂登录页没有账号密码表单，点「登录」后跳转到 SSO，字段是 `#i_user` / `#i_pass`
- 清华 OJ 本地账号密码表单实测不可用（`/api/user/login` 返回 500），
  改为展开导航栏「登录」下拉后点「使用 清华ID 登录」再进 SSO
- 顺带修复：清华 OJ 的课程名为空（现在会从课程主页标题读取，例如「离散数学 (1) 马老师课堂」）

### 4. 登录失败冷却

某个站点后台登录失败后会进入冷却，避免反复去撞 SSO：

- 需要二次验证：10 分钟内不再自动尝试
- 账号密码错误：30 分钟内不再自动尝试
- 其余原因：5 分钟

冷却表只放在内存中，重启程序即清空。手动点「登录」不受冷却限制。

### 5. 登录成功的判定要导航复核

清华 OJ 登录完成后会停在站点首页（`/`），而作业在 `/course/8/home`，
在首页上抠不到作业会被误判成「未登录」，导致一路轮询到超时（实测踩到过）。
因此校验函数在直接判断失败时，会再导航到站点目标页复核一次；
但**停在登录页或二次验证页时绝不导航**——否则会把「需要人工验证」的现场冲掉，
反而判定不出 MFA。

### 6. 账号密码加密存储

`sites.yaml` 里的账号和密码改用 **Windows DPAPI** 加密，存成 `enc:v1:<base64>`：

- 密钥由 Windows 按当前登录账户托管，程序能自行解密 → 不影响开机后台自动抓取
- 换电脑 / 换 Windows 账户则解不开，设置界面会显示「密码需重填」并提示重新填写
- 旧配置里的明文会在**启动时自动加密**（`upgrade_plaintext_credentials()`），用户无感
- 兼容性：没有 `enc:v1:` 前缀的值一律按明文处理，旧文件可无缝继续用

涉及文件的改动：`core/secrets.py`（新增）、`adapters/auth.py`（`_plain()` 解密 + 
`credentials_broken()`）、`core/controller.py`（存取时加解密）、`core/site_runner.py`（迁移）。

**踩到的坑**：`adapters/tyche.py` 里有一个自己读 `basic_user` / `basic_pass` 的
`_creds()`，漏改成走解密，导致 Basic Auth 拿着 `enc:v1:...` 当账号发出去，
服务器返回 401、Tyche 静默登录一直失败。已改为调用 `auth.http_credentials()`。
教训：加解密改造要做一次「谁在读这些字段」的全量排查，不能只改看起来相关的那些。

### 7. 会话存盘后要复核

`silent_login()` 原来是在**当前页面**校验通过就存盘返回，但
`fetch_homeworks()` 是另开浏览器、从存盘文件重建 cookie 再校验。
存盘那一刻若会话尚未稳定，就会出现「登录成功，但立刻抓取又说需要登录」的自相矛盾。
现在存盘后会用**存出来的文件**新建一个上下文验证一次，失败则重试一次。

### 8. 并行抓取 + 去掉固定等待

**背景**：用户反馈「开程序后好久才出作业」。实测串行抓取 6 个站点要 **28~35 秒**。

**优化 1：去掉固定等待和 networkidle**

`wait_for_load_state("networkidle")` 要求网络彻底安静 500ms，而学习平台普遍有轮询/埋点
请求，会一直等到超时。实测网络学堂在 `domcontentloaded` 后 **1.3 秒**就拿到了登录态和
CSRF cookie，但 `networkidle` 还要再等 **4 秒**，代码里另有硬睡 3 秒 —— 一站白等 4.4 秒。

新增 `auth.wait_for_ready(page, condition)`：条件成立就立刻继续。各适配器改为等真正需要的东西：

| 站点 | 等待条件 |
|---|---|
| 网络学堂 | 登录态 + CSRF cookie 就绪 |
| 清华 OJ | 作业列表能抠出条目 |
| Tyche | ShowGroup 接口返回 success |
| 数你最灵 | 登录态 + 作业接口不再返回 409 |
| U 校园 | 考试接口返回 success |

**优化 2：站点并行抓取**

每个站点用独立的 Playwright 浏览器 + 独立 context，互不共享状态，可以同时跑。
`fetch_all()` 按 `_fetch_one_site()` 拆分后用 `ThreadPoolExecutor` 并发执行，
`_relogin_cooldown` 加了锁。并发数可用环境变量 `HOMEWORK_BOT_WORKERS` 覆盖。

并发数扫描（6 站点、会话有效，各测 4 轮交替进行以消除网络波动偏差）：

| 并发 | 平均 | 中位 | 最快 | 最慢 | 波动 |
|---|---|---|---|---|---|
| 1（串行） | 25.0s | 23.5s | 22.8s | 30.2s | 7.4s |
| 2 | 12.8s | 12.8s | 9.4s | 16.0s | 6.6s |
| **3（默认）** | **8.1s** | **8.0s** | 8.0s | 8.2s | **0.2s** |
| 4 | 10.2s | 10.2s | 8.4s | 11.9s | 3.5s |
| 6 | 8.1s | 9.2s | 3.3s | 10.8s | 7.5s |

并发 3 不但平均最快，**波动还只有 0.2 秒**（最稳）。并发 6 出现过「3.3 秒就返回、
但只抓到 3 条、4 个错误」——并发过高互相抢资源导致的失败，属于假快。所以默认取 3。

**效果**：会话有效时 23~30 秒 → **8 秒左右**。

**试过但否决的方案：共享浏览器**

曾想「一次抓取只启动一个浏览器、各站点共用」来省启动开销，实测后否决：

- 启动一个 Edge 只要 **0.24 秒**，新建 context 0.19 秒；6 个站点各自启动合计
  约 1.4 秒，并行下更少 —— 共享能省的不到 1 秒；
- 而 Playwright 的**同步 API 是线程绑定的**，多个 worker 线程复用同一个 browser
  会直接崩：`TargetClosedError: Browser.new_context: Target page, context or
  browser has been closed`，并伴随 `greenlet.error: cannot switch to a
  different thread`。

结论：收益极小、代价是跨线程复杂度和崩溃风险，不值得做。

### 9. 数你最灵：作业接口 409

排查「并行优化后数你最灵返回 0 条」时发现：页面刚加载完就调 `queryHomeworks`
会返回 **HTTP 409**，等约 2 秒后正常。原来的固定 sleep 恰好掩盖了这个问题，
改成条件等待后暴露出来。现在就绪条件直接以作业接口为准，不再猜时间。

- 「填账号密码」从只支持 Tyche 扩展到所有站点（雨课堂除外）
- 数你最灵增加「学校全名」输入框，并写入 `sites.yaml` 的 `school` 字段
- Tyche 的两组凭据分开：Basic Auth 账号密码 + 网站账号密码
- 改账号密码后自动清除该站点的旧会话，下次刷新用新账号登录
- 顶部提示条按原因显示不同话术（未填账密 / 需验证码 / 需扫码）
- 人工兜底窗口会先把账号密码填好，用户通常只需输入验证码
