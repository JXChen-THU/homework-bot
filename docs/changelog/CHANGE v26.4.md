## 🎯 为什么 v26.4 是转折点

前几个版本都是在「能抓到什么」上做加法（接平台、调结构）。v26.4 补的是三个**产品性质**上的短板：

### 1. 从「会话过期就得手动登录」到「填一次账号密码，之后不用管」

这是本次最核心的改动，也是这个工具能不能当「常驻后台的桌面助手」用的分水岭。

改动前：所有平台都依赖首次手动登录并保存会话，**会话一过期就得用户自己点「登录」、
在弹出的浏览器里手动操作**。用户必须时不时盯着它、随时准备接管——
这使「开机自启动 + 后台静默汇总」这个卖点名不副实。

改动后：界面上本来就是「打开就能看作业」。

### 2. 从 30 秒等到 8 秒

串行抓取 6 个平台需要 **25~30 秒**（网络差时更久）。对每次刷新都要等这么久的桌面工具来说，
这个延迟是实打实的体验问题。v26.4 把它压到 **8 秒左右**。

### 3. 从明文存密码到加密存密码

`sites.yaml` 原先以**明文**保存各平台账号密码。既然是「填好就不用管」的工具，
用户必然会把真实密码填进去，明文存储就成了必须解决的风险点。

## 🔐 重大改进一：账号密码自动后台登录

### 设计：三层递进，能自动的绝不打扰用户

新增 `adapters/auth.py` 作为统一的静默登录设施。每个适配器只需声明两样东西：

- `LOGIN`：登录页地址、账号/密码/提交按钮的选择器、勾选项等
- `is_logged_in(page, site)`：如何判断这个站点当前已登录

调度行为（`core/site_runner.fetch_all()`）：

1. 正常抓取
2. 抛 `LoginRequiredError` → **有账号密码就自动重登**
3. 重登成功 → 立刻重抓，用户完全无感
4. 仍然失败 → 报告给前端，并带上**准确的失败原因**

重登本身分三层，逐层降级：

| 层 | 方式 | 用户感知 | 适用站点 |
|---|---|---|---|
| 1 | 无头浏览器静默登录 | 完全无感 | Tyche / 数你最灵 / U 校园 |
| 2 | **屏幕外真实窗口** | 无感（窗口在屏幕坐标外） | 网络学堂 / 清华 OJ |
| 3 | 弹出可见窗口，**账号密码已自动填好** | 只需输入一次验证码 | 确实需要人工介入时 |

### 关键发现：决定因素是「有真实窗口」，不是「可见」

清华统一身份认证（SSO）在实现过程中一直是最大的障碍。最初的假设是它在
「无头 vs 可见」之间做区分，于是做了对照实验：

| 方式 | 结果 |
|---|---|
| 无头、全新上下文 | ❌ 被要求二次验证 |
| headed、窗口放在屏幕外 `(-32000,-32000)` | ✅ 直接登录成功 |
| headed 屏幕外 + CDP 最小化 | ✅ 直接登录成功 |

**结论**：SSO 挑战的是「无头浏览器」这个特征，**真实窗口即使完全不在屏幕上也会被放行**。
因此开一个真实窗口、把位置指定到屏幕坐标之外，就能做到用户全程看不见、登录照常成功。

> **为什么不用「最小化」**：窗口必须先创建出来才能最小化，创建那一瞬间仍会在屏幕中央
> 闪一下（用户实测确认）。而屏幕外位置是在**创建时**就指定的，从头到尾不出现在可见区域。
> 代价是任务栏上可能短暂出现一个图标，已在 README 中说明。

### 各平台实测结论

实现前逐个平台用真实账号实测过登录入口与可行性：

| 平台 | 登录方式 | 自动后台登录 | 实测要点 |
|---|---|---|---|
| Tyche | Basic Auth + 网站表单 | ✅ 完全自动 | `http_credentials` 自动过 Basic Auth 弹窗 + `#username`/`#password` |
| 数你最灵 | 学校 + 学号/工号 + 密码 | ✅ 完全自动 | **必须先选学校**，学校名存在 `school` 字段 |
| U 校园 | 手机号/邮箱 + 密码 | ✅ 完全自动 | 首页「登录」→ `/portal/sso/login`，需勾选用户协议 |
| 网络学堂 | 清华统一身份认证 | ✅ 屏幕外窗口 | 登录页无表单，点「登录」跳 SSO，字段 `#i_user`/`#i_pass` |
| 清华 OJ | 清华统一身份认证 | ✅ 屏幕外窗口 | 本地表单接口返回 **500**，只能走「使用 清华ID 登录」 |
| 雨课堂 | 微信扫码 | ❌ 不支持 | 扫码无法自动化，保持手动 |

**清华两站的额外优化**：既然它们的无头登录**必定**被要求二次验证（多次实测稳定复现），
就没必要每次都先跑一遍。适配器用 `LOGIN["skip_headless"] = True` 声明，
调度层直接走屏幕外窗口 —— 每站省约 10 秒，也少一次多余的 SSO 交互（降低触发风控的概率）。

### 失败时不打扰、但也不静默吞掉

- **冷却机制**：后台重登失败后进入冷却，避免反复去撞 SSO
  （需二次验证 10 分钟 / 账号密码错误 30 分钟 / 其他 5 分钟）。冷却表在内存中，重启即清空；
  手动点「登录」不受冷却限制。
- **准确的话术**：失败原因会传给前端，分别提示「未填账号密码」「需要过验证码」
  「账号或密码可能不对」「需要扫码」，而不是笼统地说「需要登录」。
- **失败检测要够快**：清华 SSO 的报错「您的用户名或密码不正确，请重试！」**不在任何
  error 类元素里**（那些元素只匹配到「忘记密码」链接），最初因此判定不出失败、
  一路轮询到超时（实测白等 60 秒）。补上「正文明确句子」检测后降到 **11.9 秒**。

### 必须解决的三个隐蔽陷阱

这三个问题都是实测中暴露出来的，不解决就会表现为「登录成功但抓不到作业」这类怪现象：

1. **会话存盘后要复核**：`silent_login()` 原先在**当前页面**校验通过就存盘返回，
   而抓取时是**另开浏览器、从存盘文件重建 cookie** 再校验。存盘那一刻若会话尚未稳定，
   就会出现「登录成功，但立刻抓取又说需要登录」的自相矛盾。
   现在存盘后会用**存出来的文件**新建上下文复核一次。

2. **登录成功的判定要导航复核**：清华 OJ 登录完成后停在站点首页（`/`），
   而作业在 `/course/8/home`，在首页抠不到作业会被误判成未登录。
   现在直接判断失败时会导航到目标页复核一次；
   但**停在登录页或二次验证页时绝不导航**——否则会把「需要人工验证」的现场冲掉。

3. **数你最灵的作业接口会返回 409**：页面刚加载完就调 `queryHomeworks` 会被拒绝
   （**HTTP 409**），等约 2 秒才正常。原先的固定 `sleep` 恰好掩盖了它，
   改成条件等待后立刻暴露。现在直接以作业接口是否可用来判断就绪，不再猜时间。

## ⚡ 重大改进二：多平台并行抓取

### 从 25 秒到 8 秒

改动前 6 个平台是**串行**抓取的，总耗时等于各站相加，实测 **25~30 秒**。

现在每个站点用独立的 Playwright 浏览器 + 独立 context（互不共享 cookie 状态），
`fetch_all()` 按 `_fetch_one_site()` 拆分后用 `ThreadPoolExecutor` 并发执行。

并发数扫描（6 站点、会话有效、各测 4 轮**交替**进行以抵消网络波动偏差）：

| 并发 | 平均 | 中位 | 最快 | 最慢 | 波动 |
|---|---|---|---|---|---|
| 1（串行） | 25.0s | 23.5s | 22.8s | 30.2s | 7.4s |
| 2 | 12.8s | 12.8s | 9.4s | 16.0s | 6.6s |
| **3（默认）** | **8.1s** | **8.0s** | 8.0s | 8.2s | **0.2s** |
| 4 | 10.2s | 10.2s | 8.4s | 11.9s | 3.5s |
| 6 | 8.1s | 9.2s | 3.3s | 10.8s | 7.5s |

并发 3 不但平均最快，**波动还只有 0.2 秒**（最稳）。并发 6 出现过「3.3 秒就返回、
但只抓到 3 条、4 个错误」——并发过高互相抢资源导致的失败，属于**假快**。所以默认取 3。

并发数可用环境变量 `HOMEWORK_BOT_WORKERS` 覆盖（设为 `1` 即退回串行）。

### 顺带去掉的固定等待

原来每站都调 `wait_for_load_state("networkidle")`，它要求网络彻底安静 500ms，
而学习平台普遍有轮询/埋点请求，会一直等到超时。实测网络学堂在 `domcontentloaded` 后
**1.3 秒**就拿到了登录态和 CSRF cookie，但 `networkidle` 还要再等 **4 秒**，
代码里另有硬睡 3 秒 —— **一站白等 4.4 秒**。

新增 `auth.wait_for_ready(page, condition)`：条件成立就立刻继续。各适配器改为等真正需要的东西：

| 站点 | 等待条件 |
|---|---|
| 网络学堂 | 登录态 + CSRF cookie 就绪 |
| 清华 OJ | 作业列表能抠出条目 |
| Tyche | ShowGroup 接口返回 success |
| 数你最灵 | 登录态 + 作业接口不再返回 409 |
| U 校园 | 考试接口返回 success |

### 试过但**否决**的方案：共享浏览器

曾想「一次抓取只启动一个浏览器、各站点共用」来省启动开销。实测后否决，理由是数据：

- 启动一个 Edge 只要 **0.24 秒**，新建 context 0.19 秒；6 个站点各自启动合计约 1.4 秒，
  并行下更少 —— **共享能省的不到 1 秒**；
- 而 Playwright 的**同步 API 是线程绑定的**，多个 worker 线程复用同一个 browser 会直接崩：
  `TargetClosedError: Browser.new_context: Target page, context or browser has been closed`，
  并伴随 `greenlet.error: cannot switch to a different thread`。

结论：收益极小、代价是跨线程复杂度和崩溃风险，**不值得做**，已回退。

## 🛡️ 重大改进三：账号密码加密存储

### 用 Windows DPAPI，而不是自己造加密

`sites.yaml` 里的账号和密码改用 **Windows DPAPI**（`CryptProtectData`）加密，
存储为 `enc:v1:<base64>`。密钥由操作系统按当前登录账户托管：

- **不影响开机后台自动抓取**：程序能自行解密，用户不需要额外输入任何密码
- **换电脑 / 换 Windows 账户则解不开**（这是特性，不是缺陷）：设置界面会显示
  红色「密码需重填」，视为未填写，**不会拿坏数据去登录**
- **旧配置自动升级**：原先的明文会在启动时自动加密（`upgrade_plaintext_credentials()`），
  用户无感
- **向前兼容**：没有 `enc:v1:` 前缀的值一律按明文处理，旧文件可无缝继续用
- 额外加了应用专属熵（`_ENTROPY`），即使拿到文件单独调 DPAPI 也解不开

### 说清楚边界

**这挡的是「文件被别人看到」**（误传网盘、被同步工具上传、误提交进仓库），
**不是「防住本机恶意软件」** —— 任何以用户身份运行的程序都能调用 DPAPI 解密。
真正要改配置时，在「设置 → 填账号密码」里改即可。

### 踩到的坑：加解密改造要做全量排查

`adapters/tyche.py` 里有一个自己读 `basic_user` / `basic_pass` 的 `_creds()`，
改造时漏掉了它，导致 Basic Auth 拿着 `enc:v1:...` 当账号发出去，服务器返回 **401**、
Tyche 静默登录一直失败。已改为统一调用 `auth.http_credentials()`。

**教训**：加解密改造必须做一次「谁在读这些字段」的全量排查，
不能只改那些看起来相关的调用点。

### 顺带修掉一个真实的凭据泄漏

排查中发现项目根目录有一个早期调试日志 `real_tyche.log`，
里面以**明文**记录了账号密码（`basic_pass = '***REMOVED-BY-v26.5-CLEANUP***'` / `password = '***REMOVED-BY-v26.5-CLEANUP***'`）。
它没有被任何代码引用，也未进过 git，但确实是个泄漏点，已删除并对
**整个仓库跟踪文件 + 工作区**做了明文凭据全盘扫描，确认无残留。

## 🚫 为什么不记日志（有意为之，别再补上）

复审曾建议「建立日志文件 + 重定向 stdout + 接三个 excepthook」，
理由是「出问题时查不到原因」。这个出发点是对的，但**结论不适用于本项目**：

1. **排障只需要一份 exe 和一个人的判断。** 这个工具的使用者就是作者本人，
   不需要靠日志做远程支持；出了问题可以直接复现。
2. **日志会引入新的磁盘风险。** 实测踩过一次：日志写入方式有缺陷
   （同一份文件被两个句柄写，且验证脚本「读日志又打印」形成自我反馈），
   几分钟内涨到 **194 GB**，把整个 D 盘占满。这类风险在没有日志时不存在。
3. **出问题时真正需要的是「让用户看见」**，而不是「写进文件」——
   已用系统消息框覆盖（见下方第 1 条）。

所以现在的取舍是：**不写任何日志文件**，只在
「界面无法启动」这种用户必须知道的情况下弹中文提示框。
`print` 仍在代码里，源码模式运行时能在控制台看到。

> 如果将来真的需要日志，务必注意两点：
> **① 全项目只允许一个写入句柄**（不要一边用 `RotatingFileHandler`、
> 一边又自己 `open()` 同一个文件）；
> **② 绝不「读日志文件并打印」**——读写同一个文件会形成自我反馈。

## 🔍 发布前复审：查出并修掉的发布级缺陷

v26.4 完成后做了一轮独立复审，以下是**经代码核实后采纳**的修复。

### 1. 界面启动失败时毫无提示

打包配置是 `console=False`，窗口化运行时既没有控制台可看。
原先 `webview.create_window` / `webview.start` **不在 try 里**，
目标机缺少 Microsoft Edge WebView2 运行时时异常直接抛出，
用户只看到「程序双击后没反应」，无从知道原因。

现在把 GUI 初始化包进 `try/except`，失败时用系统消息框弹出
**中文、可操作**的提示（告知缺少 WebView2 运行时及安装办法）
并以非 0 退出码退出。

> 说明：本项目**不写日志文件**（有意为之，见下方「为什么不记日志」）。

### 2. 程序放在受保护目录时可能完全起不来

`controller.py` 与 `site_runner.py` 原先都在**模块导入期**就
`os.makedirs(DATA_DIR)`，而 frozen 时 `BASE` 是 exe 所在目录。
用户若把程序解压到 `Program Files`、`C:\` 根等位置，
导入期就抛 `PermissionError`，**连界面都出不来**。

现在导入期只解析路径、不建目录；目录创建与可写性探测推迟到 `main()`，
不可写时回退到 `%LOCALAPPDATA%\HomeworkTasks`。
**回退绝不静默**：会把原有 `sites.yaml` 与 `data/` 非破坏性复制过去，
并在界面上明确告知新位置。

### 3. 会话文件损坏后永远无法自愈

`_fetch_one_site()` 原先把 `fetch_homeworks()` 的**任何**异常都归入
`errors` 并直接返回，于是永远走不到后面的重登分支。
而会话文件被写坏时，Playwright 抛的正是通用异常 ——
结果是该站点**每次刷新都失败，只能靠用户手动删文件**。

现在检测到「会话文件存在但读不出合法 JSON」时会删除它并转入重登，
实现自愈。实测：把 `thu_session.json` 截断成半截 JSON，
程序自动重登并抓回 5 条作业。

### 4. 并发与文件完整性

- **同一站点可能被两条路径同时操作**：刷新（线程池）与手动点「登录」
  （js_api 线程）。两者都会跑完整登录流程（≥10 秒），
  若并发会拉起两个浏览器并互相覆盖会话文件。
  现在按站点加锁，用 `RLock`（`login_site` 会调用 `auto_relogin_site`，
  普通 `Lock` 会自死锁）。
- **会话文件与 `sites.yaml` 原先都是直写**（`open(...,"w")` 会先 truncate），
  读方可能读到半截内容。现在统一改为「写临时文件 + `os.replace`」原子替换，
  `sites.yaml` 另外保留 `.bak` 备份，损坏时可回退。
- **写失败不再只 print**：`save_sites` 的失败会回传到界面，
  避免出现「UI 说保存成功、文件其实没变」。

### 5. 前端按钮的承诺与实际动作不符

顶部提示条上，`bad_credentials` 的按钮写着「重新填账号密码」，
但点击后对所有 reason 都走同一个 `api.login()` —— **弹出浏览器窗口**。
`session_unstable` 的「重试登录」同理。

现在按 reason 分流：`bad_credentials` 直接打开凭据填写弹窗，不弹浏览器。

### 6. 前端对 js_api 失败零处理

`await window.pywebview.api.login(...)` 没有 try/catch。
pywebview 会把 Python 异常变成 rejected promise，于是按钮会
**永久停在 disabled 的「正在打开登录窗口...」**，只能重开程序。
现在所有 js_api 调用都包了 try/catch，失败时恢复可点击状态。

同时删除了一处死分支：`main.js` 判断 `r.error === 'need_credentials'`，
但 `Api.login()` 只返回 `{"ok": ...}`，该分支永远不会命中。

### 7. 加密相关的两处小问题

- `_plain()` 在「解密模块导入失败」时返回原值，会把 `enc:v1:…` 当明文
  填进登录表单，与它自己文档承诺的「返回空串」矛盾。
- `core/secrets.py` 用 `ctypes.windll` 加载 crypt32，未设
  `use_last_error=True`，导致 `ctypes.get_last_error()` **恒为 0**，
  报错时拿不到真正的 Win32 错误码。已改为 `ctypes.WinDLL(..., use_last_error=True)`。

### 复审中评估后**未采纳**的一条

复审提出「清华 SSO 的二次验证会被误判成密码错，进而按 30 分钟冷却、
并误导用户去改一个本来正确的密码」，定级为高。

**代码顺序问题属实**（正文错误扫描确实在 MFA 判断之前），
**但结论经实测否掉了**：用真实账号触发二次验证页后，把 12 个错误标记
逐个与页面正文比对，**全部未命中**（该页正文是
「…本次登录需要进行二次验证。请选择以下方式之一获取验证码…」）。
即当前代码在这种情况下会正确返回 `mfa`，不存在所述连锁后果。

因此**未按该条描述去改**（避免为不存在的问题改动 MFA 判定路径），
仅记录在案；若将来新增站点出现误判，再按「先判 MFA、再扫正文」处理。

## 🔧 修补：三处前端「静默吞掉失败」（v26.4 补丁）

这一批都不是崩溃，而是**失败被吞掉、界面报出与实际相反的结果**。

### 1. 数据目录回退提示永远不显示（`Work\web\main.js`）

`core/paths.py` 的 `startup_messages()` 在程序目录不可写时会产出一段中文说明

前端「应用」按钮的回调**连返回值都没有接收**，无条件显示绿色「✓ 已应用」。

**用户可见后果**：`sites.yaml` 写入失败（目录只读、被杀毒软件占用、磁盘满）时，

`refreshAutostart()` 里那段「读取失败」提示只在 `catch` 里，而这条路径

**用户可见后果**：注册表读不到（权限、安全软件拦截、项损坏）时，

## 🔧 修补二：浮窗数据流（v26.4 补丁）

### 4. 浮窗最小化后数据永久停止更新

`layout_all()` 把「显示/定位窗口」和「向前端注入数据」写在同一个
`if not _alert_minimized:` 分支里。用户把红窗缩到任务栏后，该标志置真且
**除 `reset_floating()` 外没有任何清除路径**（浮窗没有注册 `restored` 事件），
于是从任务栏拉回来的窗口永远停在最小化之前那一批任务：
已经完成的作业还列在里面、倒计时永远冻结、新任务不再出现。
更极端的情况下 `urgent` 变空会让 `layout_all` 走 `hide()`，
用户刚拉出来的窗口当场消失且再不会出现。

**修复**：抽出 `_inject_urgent()` / `_inject_normal()` 并把调用移到最小化
判断**之外**（最小化只跳过显示/定位，不再跳过数据）；给两个浮窗注册
`events.restored` 回调 `_on_float_restored()`，从任务栏恢复时清掉标志并重排。

### 5. 任务链接可点（此前全链路产出、界面零消费）

6 个适配器都抓了原网页链接，手动任务的「链接」输入框也专门让用户填，
但主列表从不渲染它 —— 用户填了等于白填，抓到的作业深链也白抓。

**修复**：
- 后端新增 `Api.open_url(url)`，用系统默认浏览器打开，只放行 `http(s)`
  （拒绝 `file://`、`javascript:` 等伪协议），失败走 `{"error": ...}`。
  不用 `<a target="_blank">` 是因为那让 WebView2 自己导航，
  题目站点普遍要求登录态，只会弹出空白页；交给系统浏览器能复用已登录会话。
- 前端 `render()` 对有链接的任务把标题渲染成可点元素，
  点击调 `open_url`，失败弹提示。

### 已知但**未改**：浮窗全关 + 主窗口被藏后没有入口

浮窗上的「主面板」按钮会 `hide_main()`（主窗口连任务栏条目一起消失），

## ✨ 新功能：抓取进度文字区 + 启动行为开关

### 需求 A：抓取时的进度文字区

抓取期间在**任务列表上方**出现一行行状态文字，显示「正在发生什么」；
抓完收起、内容清空，把空间还给任务列表。

外观上就是**文字落在原来的底版上**：不加底色、不加边框、不加圆角，
与顶部「任务刷新中」是同一种观感（13px、无背景）。
每行形如 `[站点名] 开始抓取`，其中**方括号部分（含站点名）用蓝色**，
其余正文黑色；站点名用等宽字体以便和正文对齐。

- **只允许 3 类行**：`检查网络… 已连接` / `[站点名] 开始抓取` /
  `[站点名] 完成 N 条`（或 `需要登录` / `抓取失败`）。
  适配器内部的调试输出（`[silent-login]`、`[relogin]`、`[wait]` 超时、
  英文错误码、选择器字符串）**一律不透出来** —— 播报逻辑在
  `site_runner._fetch_one_site_locked()` 的返回点，不碰 7 个适配器。
- **行为**：最多 3 行，新的顶掉最旧的，自动滚到底；
  相邻两行最小间隔 150ms，但区域为空时前 3 行立即输出（不拖首屏）。
- **无时间戳、无总耗时、无进度条、无「第 N/M 个」**。

实现要点（都是踩过的坑）：

| 注意点 | 原因 |
|---|---|
| 容器放在 `#content` **外面** | `render()` 每次都整块重建 `#content` 的 innerHTML，放里面会被每次重绘冲掉 |
| 必须走 `evaluate_js` 推送 | 放进 `get_homeworks()` 返回值的话，promise 要抓完才 resolve，用户全程看不到东西 |
| 推送前必须确认 `_main_ready` | pywebview 的 `evaluate_js` 带 `@_shown_call`，未就绪会先白等 20 秒再抛异常 |
| 播报点只有一个函数、多个返回点 | `_fetch_one_site_locked()` 有 6 个 return，逐个补播报由测试守护 |
| 抓取加了串行锁 `_fetch_lock` | 连点刷新时两轮进度行会交叉串台 |
| 方括号单独包 `<span class="br">` | 只给中括号染蓝，其余保持黑色；用 `textContent` 逐段赋值，不走 innerHTML |

### 需求 B：设置里的「启动行为」两个开关

设置里合并成一个「🚀 启动行为」区块，两个开关与「开机自启动」**同一套样式**
（`.switch`），没有灰色说明文字：

| 开关 | 开 | 关 |
|---|---|---|
| **开机自启动** | 每次开机并联网后自动启动 | 不开机自启 |
| **启动时静默** | 启动不出现窗口（`startup_mode: silent`，默认） | 启动即显示界面（`visible`） |

值存在 `sites.yaml` 的顶层键 `startup_mode`（`silent` / `visible`），
老配置没有这个键时用默认值 `silent` 兜底。

「启动时静默」的开关状态**在启动时就主动读一次后端**，而不是等打开设置面板
才读 —— 开关没有「默认勾选」这回事，不主动读的话第一次打开设置面板时
开关是空的。

**`minimized=True` 达不到静默效果**：pywebview 只设 `WindowState`，
窗口仍走 `browser.Show()`，会真实显示一瞬再缩进任务栏 → 任务栏图标闪一下。
改成 `hidden=True`（`Opacity=0 → Show() → Hide()`，肉眼看不到）。

**关键发现（文档里原本没写）**：`hidden=True` 的实现里**仍然会调用
`Show()`**，因此 WinForms 的 `Shown` 事件照常触发 → pywebview 的
`evaluate_js` 的 `@_shown_call` 门禁能通过，隐藏窗口推数据不会卡 20 秒。
这条是这个方案能成立的前提。

同步对齐了三处「会自动显示窗口」的地方：

1. `get_homeworks()` 首次显示 → 静默档不显示；
   **直接显示档改为在抓取之前显示**（否则等抓完才显示，用户看不到滚动过程，
   而需求 B 的核心就是让用户看着它滚）。
2. `_startup_show_fallback()` 300 秒兜底 → 静默档不再弹窗
   （用户选了「每次启动都不出现窗口」，到点自动弹出来直接违背选择）。
3. `show_main_window()` 各调用点（用户点「主面板」/「重置浮窗」）行为不变。

`save_sites()` 原先直接写 `{"sites": [...]}`，会把 `startup_mode`
这类顶层键整块抹掉 —— 已改为「只替换站点数组，保留其它顶层键」。
不修的话，用户点一次「应用」，启动行为设置就悄悄回到默认值。
